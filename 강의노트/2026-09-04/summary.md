# 데이터베이스 — 서비스의 '기억'을 만들고, 지키고, 고르기

## 핵심 요약
- 지난 시간의 백엔드가 '주방'이었다면 오늘은 **재료를 두는 창고**다. 지금까지 다룬 목업 데이터는 메모리에만 있어 새로고침하면 사라졌고, 서비스가 되려면 껐다 켜도 남는 영구 창고 — **데이터베이스** 가 필요하다. DB는 그냥 쌓아 두는 곳이 아니라 **원하는 것만 빠르게 찾아 주는 곳**(도서관·사서 비유)이고, 엑셀과 달리 규칙(스키마)을 강제하고 대량 데이터에서도 빠르며 여러 사람이 동시에 안전하게 쓸 수 있다.
- DB 종류가 많은 건 어렵게 만들려는 게 아니라 **시대마다 병목이 달랐기 때문**이다. 1960년대 파일 → 1970년 에드거 코드의 관계형 논문(표로 나누고 관계로 잇기) → 1974년 SEQUEL(상표 문제로 SQL 로 개명) → 1979년 오라클의 첫 상용 관계형 DB → 2000년대 NoSQL → 오늘날 클라우드 DB 로 이어지며, NoSQL 은 'No SQL' 이 아니라 **'Not Only SQL'** — 관계형을 대체한 게 아니라 용도별 선택지다.
- SQL 은 **거의 영어 문장**이라 외울 필요 없이 알아보기만 하면 된다(`SELECT 이름, 가격 FROM 상품 WHERE 분류 = '케이크'`). 동작은 **CRUD** 네 가지뿐이고, 데이터의 모양은 **표·행·열 + 키로 잇기**로 이해하면 된다. 표를 잇는 모양은 1:N(칸 하나 추가)과 N:M(연결 표 신설) 둘이며, 같은 정보를 한 곳에만 두는 정리정돈이 **정규화**, 빠르게 찾는 장치가 **색인(책 뒤 찾아보기)**, 반쪽 실행을 막는 묶음이 **트랜잭션(ACID)** 이다.
- 사용자가 생기면 다루는 것도 늘어난다. 회원가입·로그인은 결국 회원 표에 대한 CRUD 이며 **비밀번호는 해시(솔트+bcrypt)로, 이메일은 유일 제약으로, 수집은 최소한으로** 가 원칙이다. 로그인 유지는 **세션(서버가 기억, 즉시 차단 가능)** 과 **토큰/JWT(서버가 기억 안 함, 확장에 강함)** 두 갈래인데 — 결론은 **직접 만들지 말고 검증된 Auth 서비스에 맡기라**는 것이다. 세션 저장소로는 자동 만료(TTL)가 되는 Redis 가 잘 맞는다.
- 데이터를 모으는 순간 **훔쳐 가는 것(보안)** 과 **실수로 날아가는 것(백업)** 두 위험이 따라온다. SQL 주입은 25년 넘게 위협 1위권이지만 방어법은 확실하다 — **명령과 입력을 섞지 않는 파라미터화 쿼리**. 백업은 **3-2-1 규칙**(3벌·2종·1벌은 다른 장소)이고, 픽사·GitLab 사고가 보여주듯 **"있다고 믿었지만 고장 나 있던"** 백업이 진짜 위험이라 복구 확인이 필수다. 무료 DB 는 배우기·MVP 용이며 한도·일시정지·백업 포함 여부·정책 변경을 가입 전에 확인해야 한다.

## 상세 내용

### 1. 데이터를 저장할 곳이 필요한 이유
지난 시간에 백엔드(눈에 안 보이는 주방)를 봤지만 한 가지가 빠져 있었다 — 만든 데이터를 어디에 둘 것인가. 지금까지 다룬 목업 데이터는 컴퓨터의 잠깐 기억(메모리)에만 있어서 껐다 켜거나 새로고침하면 사라진다. 서비스가 되려면 데이터가 남아야 하고, 그 영구 창고가 데이터베이스다.

DB 를 이해하는 데는 두 그림이면 충분하다. **도서관** — 책이 수만 권이어도 원하는 책을 금방 찾는다(DB=도서관, 데이터=책, 관리 소프트웨어=사서). **마법 장난감 상자** — 마구 넣어도 "파란색 자동차만 꺼내 줘" 하면 그것만 정리해 준다. 핵심은 DB 가 쌓아 두는 곳이 아니라 **원하는 것만 빠르게 찾아 주는 곳**이라는 점이다.

엑셀·메모장과의 차이는 세 가지다. ① **규칙(스키마)이 있다** — "이 표에는 이름·가격·분류가 들어간다"처럼 모양을 정해 두고 강제해서 뒤죽박죽이 되는 걸 막는다. ② **수만 건에서도 순식간에 찾는다** — 엑셀은 커지면 느려지고 멈추지만 DB 는 그러라고 만들어졌다. ③ **여러 사람이 동시에 안전하게 쓸 수 있다**.

규모 감각을 주는 사례도 나온다. 미국 의회도서관은 1억 7,800만 점 이상을 소장하고 디지털 보존만 페타바이트 단위다. CERN 의 LHC 는 초당 약 10억 번의 입자 충돌로 이론상 초당 1페타바이트가 쏟아지지만 '트리거'가 의미 있는 1% 미만만 골라 저장하며, 그렇게 걸러도 2023년에 저장 용량 1엑사바이트를 넘었다 — **큰 데이터에서는 무엇을 저장할지 고르는 일이 저장장치 크기만큼 중요하다**는 뜻이다. 다만 오늘날의 요점은 규모 자랑이 아니라, 클라우드 덕분에 비전공자도 이 거대한 기술을 무료로 조금 빌려 쓸 수 있게 됐다는 것이다.

오늘의 핵심 한 문장은 이렇다 — **데이터베이스는 서비스의 '기억'이다. 넣고 꺼내는 코드(SQL)는 AI 가 쓰지만, 무엇을 어떤 모양으로 저장할지·어떤 DB 를 고를지·어떻게 안전하게 지킬지는 내가 정한다.**

### 2. 왜 종류가 많을까 — 데이터베이스의 역사
엑셀에 주문을 적던 두 사람이 같은 행을 동시에 고쳐 하루 주문이 꼬이는 장면에서 시작한다. **데이터를 함께 쓰면서 바뀐 내용을 잃지 않으려는 문제**가 데이터베이스를 낳았다. 프레임워크가 그랬듯 DB 도 매 시대 병목이 달라 새 도구가 쌓여 온 것이다.

연표는 이렇다. **1960년대** 파일에 쭉 적어 두다 양이 늘자 찾기가 번거로워졌다. **1970년** IBM 연구원 에드거 코드가 "데이터를 표로 나누고 표끼리 관계로 잇자"는 논문을 냈다 — 같은 정보를 중복해 적지 않아도 되게 한 혁신이었다. **1974년** 표에 말을 거는 언어 SEQUEL 이 등장했고(뒤에 SQL 로 개명), 50여 년이 지난 지금도 거의 그대로 쓰인다. **1979년** 첫 상용 관계형 DB(오라클). **2000년대** 데이터 폭증과 형태 다양화로 NoSQL 등장. **오늘날** 클라우드가 운영까지 대신해 비전공자도 무료로 진짜 DB 를 쓴다.

강의는 네 가지 뒷이야기를 곁들인다. ① **코드의 표 혁명과 IBM 의 망설임** — 당시 데이터는 나뭇가지처럼 얽힌 구조라 꺼낼 때마다 전용 프로그램을 짜야 했다. 코드는 "그냥 표로 두고 관계로 이으면 안 되나"라는 논문을 냈지만, 정작 IBM 은 잘 팔리던 기존 제품(IMS)을 갉아먹을까 봐 미지근했다. ② **'SQL'은 원래 '시퀄'** — SEQUEL(Structured English Query Language)이 영국 항공기 회사 상표와 겹쳐 모음을 뺀 것이 SQL 이다. 만든 사람들조차 "시퀄"이라 부르니 어느 발음을 들어도 둘 다 맞다. ③ **IBM 보다 빨랐던 신생 회사** — 코드의 논문을 읽고 "돈이 되겠다"고 확신한 래리 엘리슨이 1977년 창업해 1979년 첫 상용 관계형 DB 를 내놨다. IBM(1981년)보다 2년 앞섰고, 첫 제품 버전을 신뢰감을 주려고 '1'이 아닌 '2'로 붙였다. ④ **NoSQL 의 진짜 뜻** — 구글 Bigtable(2006)·아마존 Dynamo(2007)가 표의 엄격함을 조금 포기하고 규모와 속도를 얻는 방식을 공개했고, 2009년 개발자 모임에서 검색하기 좋은 이름으로 'NoSQL'이 붙었다. 이 이름이 "SQL 쓰지 말자"로 오해를 사면서 나중에 **'Not Only SQL'** 로 재해석됐다.

성격 비교는 문법 없이 이렇게 정리된다.

| | SQL | NoSQL |
|---|---|---|
| 생김새 | 엑셀 같은 표 | 유연한 문서/덩어리 |
| 규칙(스키마) | 엄격 | 느슨하거나 없음 |
| 강한 곳 | 관계가 분명한 데이터, 정확성(돈·주문) | 대규모·빠르게 변하는 데이터 |
| 대신 포기 | 유연함이 덜함 | 조인·엄격한 거래 일부 |

넷플릭스·우버 같은 큰 서비스도 둘 다 쓴다(용도별로 골라 쓰는 것을 '폴리글랏'이라 한다). 다만 **처음 만드는 서비스라면 SQL 이 무난한 기본값**이다.

### 3. SQL 구경과 데이터의 모양
카페 사장님이 "오늘 케이크 주문만 보고 싶다"고 하는데 주문이 수백 건이면 눈으로 찾기 어렵다. 조건에 맞는 데이터만 골라 달라고 DB 에 요청하는 언어가 SQL 이고, 겁먹을 것 없이 거의 영어 문장이다.

```sql
SELECT 이름, 가격 FROM 상품 WHERE 분류 = '케이크';
```

풀어 읽으면 "상품 표에서(FROM) 분류가 케이크인 것들의(WHERE) 이름과 가격을 줘(SELECT)"다. 넣고·고치고·지우는 것도 단어만 바뀐다 — `SELECT`(조회) · `INSERT`(넣기) · `UPDATE`(고치기) · `DELETE`(지우기). 이 넷을 묶어 **CRUD** 라 하고, 대부분의 서비스는 결국 이 네 동작의 반복이다. 외울 필요 없이 "이 표에서 뭘 꺼내는(넣는) 거구나"를 **알아보는 정도면 충분**하다.

**표로 생각하기.** 관계형 DB 는 결국 표다 — 표 하나 = 한 종류(상품 표), 행 = 한 건(딸기 케이크 하나), 열 = 항목(이름·가격·분류). 그리고 표끼리 **관계**로 잇는데, 주문 표는 상품 정보를 통째로 베끼지 않고 각 상품의 고유 번호(ID)로 가리킨다. 이 "표로 나누고 관계로 잇기"가 **관계형(relational)** 이라는 이름의 뜻이고, 표를 잇는 번호를 **키(key)** 라 한다.

쇼핑몰을 예로 한 덩어리로 뭉치면 "홍길동이 3월 2일에 초코케이크 2개를 12,000원에 샀고, 홍길동 주소는…"이 되어 주문 100건이면 주소가 100번 적힌다. 그래서 성격이 다른 것끼리 표를 나눈다 — 회원(사람 정보) · 상품(파는 것) · 주문(언제 누가 무엇을). 핵심은 주문 표가 이름·주소를 다시 적지 않고 "1번 회원"이라고만 가리키는 것이다. 주소가 바뀌면 회원 표 한 곳만 고치면 끝난다.

**표가 이어지는 두 모양.** ① **일대다(1:N)** — 회원 1명은 주문을 여러 건 남기지만 주문 1건은 한 회원의 것이다. 주문 표에 "누구의 주문인지" 칸 하나만 넣으면 된다(블로그 글 1개 ↔ 댓글 여러 개, 채널 1개 ↔ 영상 여러 개가 같은 모양). ② **다대다(N:M)** — 학생 1명은 여러 수업을 듣고 수업 1개도 여러 학생이 듣는다. 양쪽 어디에도 상대를 다 적을 수 없으니(한 칸에 여러 개를 욱여넣으면 검색이 깨진다) **연결 표**(수강신청 표)를 새로 만들어 학생 번호와 수업 번호를 짝지어 한 줄씩 적는다. 그러면 N:M 이 '연결 표를 사이에 둔 두 개의 1:N' 으로 풀린다. 판단 감각은 하나면 된다 — **"A 하나가 B 여럿을, 동시에 B 하나도 A 여럿을 갖나?"**

**색인(index).** DB 가 빠른 비결은 전공책 맨 뒤의 '찾아보기'와 같다. "삼투압 → 245쪽" 덕에 처음부터 넘기지 않고 바로 간다. 자주 찾는 항목(이메일·상품명)에 색인을 만들어 두면 수백만 건에서도 순식간에 찾고, 없으면 처음부터 전부 뒤진다. 다만 **공짜가 아니다** — 넣고 고칠 때마다 색인도 갱신해야 하고 공간도 든다. 그래서 빠른 DB 는 색인이 많은 DB 가 아니라 **실제 질문에 맞는 최소한의 색인**을 가진 DB 다. 실전 요령은 AI 에게 "색인 넣어줘"가 아니라 **"사용자는 자기 주문만 최근순 20개 본다"** 처럼 실제 화면의 질문을 문장으로 주는 것이다.

**트랜잭션과 ACID.** A 가 B 에게 만 원을 보낼 때 ① A 에서 빼기 ② B 에 넣기 사이에 정전이 나면 만 원이 증발한다. DB 는 이를 막으려 여러 동작을 하나의 묶음(**트랜잭션**)으로 처리하며 원칙은 하나 — **"전부 되거나, 전부 안 되거나."** 이 성질을 포함한 네 약속이 **ACID**(1983년 명명)다 — **원자성**(반쪽 실행 없음) · **일관성**(규칙 어긋난 상태로 안 끝남) · **고립성**(동시에 만져도 안 꼬임) · **지속성**(정전에도 남음). 마지막 티켓 한 장을 두 명이 동시에 눌러도 둘 다에게 팔리지 않게 하는 것이 이 장치다. 외울 것은 하나 — **돈·주문·예약처럼 틀리면 큰일인 데이터는 SQL DB 가 안전하다.** 그리고 **ACID 는 백업이 아니다** — 실수로 지운 건 되돌려 주지 않는다.

**정규화.** 단골 손님 주소가 바뀌었는데 주문 100건에 주소를 따로 적어 뒀다면 100군데를 고쳐야 하고 하나라도 놓치면 어긋난다. 그래서 관계형 DB 는 "같은 정보는 한 곳에만 적고 나머지는 그걸 가리키게" 한다. 이 중복 제거 정리정돈이 **정규화(normalization)** 이며, 실무에서 필요한 건 **"이 정보, 여기저기 똑같이 적히고 있진 않나?"** 라는 의심 하나다.

**마이그레이션.** 서비스가 자라면 표 구조 자체를 바꿔야 할 때가 온다(칸 추가·표 분리). 이미 데이터가 든 DB 의 구조를 안전하게 바꾸는 작업이 **마이그레이션**이고, "DB 구조 변경을 Git 처럼 이력으로 관리하는 것"이라 생각하면 된다(되돌리기도 된다). 딱 하나 기억할 것 — **칸을 삭제하는 변경은 그 안의 데이터가 영구히 사라질 수 있으므로 구조를 바꾸기 전엔 반드시 백업.**

**NoSQL 네 갈래.** 이름과 쓰는 곳만 알면 된다.

| 종류 | 한 줄 | 대표 | 어떤 곳에 |
|---|---|---|---|
| 문서(Document) | JSON 처럼 자유로운 덩어리 | MongoDB | 형태가 자주 바뀌는 데이터, 프로필·카탈로그 |
| 키-값(Key-Value) | "이름표 → 값", 단순·초고속 | Redis, DynamoDB | 장바구니·세션·캐시 |
| 컬럼(Column) | 대량 분석에 강한 열 중심 | Cassandra, HBase | 로그·대규모 통계 |
| 그래프(Graph) | 점과 선으로 '관계'를 저장 | Neo4j | 소셜 네트워크("친구의 친구") |

선택 기준은 한 줄이다 — 표로 잘 정리되고 관계가 분명하면 **SQL**, 형태가 자주 바뀌고 아주 대규모면 **NoSQL**. 비전공자의 첫 서비스 기본값은 **PostgreSQL** 이 무난하다(자료가 가장 많고 유연한 형식도 지원해 나중에 곤란해질 일이 적다).

### 4. 회원가입과 로그인 — 사용자를 다루기
서비스에 사람이 로그인하기 시작하면 다룰 것이 훅 늘어난다. 원리(인증·인가·쿠키/세션)는 지난 시간에 봤으니 여기서는 **데이터·저장 관점**으로 잇는다.

**회원가입·로그인은 결국 CRUD 다.** 회원(users) 표에 `id · email · password_hash · created_at` 같은 열을 두고, 회원가입 = 행 하나 넣기(Create), 로그인 = 그 이메일로 행을 찾아(Read) 비밀번호 대조다. 꼭 지킬 세 가지는 ① **비밀번호를 절대 원문으로 저장하지 않는다** — 칸 이름을 `password` 가 아니라 `password_hash` 로 두면 "원문 금지"를 스스로 상기하기 좋다. ② **이메일은 유일(unique) 제약**을 걸어 중복 계정을 막는다. ③ **필요한 것만 모은다.** 그리고 **인증은 직접 만들지 말 것** — 로그인·비밀번호 재설정·소셜 로그인은 함정이 많아 자작하면 사고로 이어지기 십상이라, 검증된 Auth 서비스(Supabase Auth 등)를 쓰는 게 안전하다.

**로그인 상태 유지 — 세션 vs 토큰.** HTTP 는 무상태라 매 요청이 남남이어서 매번 '나 아까 그 사람'을 증명해야 하고, 그 증명을 실어 나르는 게 쿠키다. 여기서 두 갈래가 갈린다. **세션** 은 서버가 로그인 상태를 자기 저장소에 적어 두고 브라우저엔 번호표(세션 ID)만 준다 — 서버가 상태를 쥐고 있어 **로그아웃·강제 차단을 즉시** 할 수 있지만, 서버가 여러 대로 늘면 저장소를 나눠 써야 한다. **토큰(JWT)** 은 사용자 정보와 만료 시각을 담아 위조 못 하게 서명한 증명서를 통째로 내주고, 서버는 저장소를 뒤질 필요 없이 서명만 확인한다 — 확장·연동에 강하다. 단, **토큰 내용은 암호가 아니라 그냥 인코딩**이라 가진 사람은 누구나 열어 본다(서명이 막는 건 '못 바꾸게'이지 '못 보게'가 아니다) — 민감정보를 넣으면 안 된다. 또 한 번 내준 토큰은 즉시 무효화가 어려워 보통 만료를 짧게 두고 리프레시 토큰으로 갱신한다. 단순한 웹앱이고 즉시 차단이 중요하면 세션이, 여러 서비스·모바일·큰 확장이면 토큰이 유리하다. 실용 결론은 역시 **직접 만들지 말라**는 것이다 — MDN 조차 세션 관리를 직접 구현하지 말고 검증된 라이브러리를 쓰라고 못 박는다.

**캐시와 Redis.** 캐시는 자주 쓰는 데이터를 메모리에 잠깐 두어 빠르게 꺼내는 것으로, 계산대 옆 바구니에 비유된다. 속도를 얻는 대신 원본과 잠깐 어긋날 수 있어 수명(TTL)을 정해 둔다. 로그인에서 캐시가 등장하는 자리가 **세션 저장소**다 — 세션 확인은 거의 모든 요청마다 일어나 빠름이 생명인데, 키-값 메모리 DB 인 **Redis** 가 조회가 매우 빠르고 키마다 자동 만료(TTL)를 걸 수 있어 '30분 활동 없으면 자동 로그아웃'을 손쉽게 만든다. 즉 "세션을 여러 서버가 나눠 쓰는 문제"와 "캐시로 속도를 얻는 것"이 도구 하나로 만난다. 보안 메모로, 브라우저의 `localStorage` 는 악성 스크립트(XSS)에 그대로 읽혀 위험하므로 OWASP 는 자바스크립트가 못 읽는 **httpOnly 쿠키**를 권한다.

### 5. 데이터를 안전하게 — 보안과 백업
데이터가 쌓이면 두 위험이 따라온다 — **누가 훔쳐 가는 것(보안)** 과 **실수로 날아가는 것(백업)**.

**SQL 주입과 "Little Bobby Tables".** xkcd(2007)의 전설적인 만화에서 학교가 전화한다 — "아드님 이름을 DB 에 넣었더니 학생 기록이 전부 지워졌어요." 엄마가 답한다 — "우리 아들 이름이 `Robert'); DROP TABLE Students;--` 라서요. 앞으로는 입력값을 꼭 검증하시길." 이름에 DB 명령어처럼 생긴 문자가 들어 있었고 프로그램이 그걸 **이름이 아니라 명령으로 실행**해 학생 표를 통째로 삭제한 것이다. 이것이 **SQL 주입**이며 25년 넘게 보안 위협 1위권을 지킨다.

방어법은 확실하다 — **"레시피와 재료를 섞지 않는다."** 사용자가 친 글자를 명령 문장에 그대로 이어 붙이면 DB 가 "어디까지가 명령이고 어디부터가 데이터"인지 헷갈린다. 대신 자리표(`?`)를 비워 둔 명령을 만들고 입력을 따로 건네면 DB 가 입력을 무조건 데이터로만 취급한다. 이 방식이 **파라미터화 쿼리(prepared statement)** 이고 OWASP 가 꼽는 표준 방어법이다. AI 에게는 이렇게 요구하면 된다 — *"DB 에 넣는 값은 문자열로 이어 붙이지 말고 파라미터화 쿼리로 처리해줘."*

실화도 뼈아프다. 2015년 영국 통신사 **TalkTalk** 이 SQL 주입으로 뚫렸는데, 공격자는 대단한 조직이 아니라 **모두 21세 미만**이었고 이용된 구멍은 **3년 반 전에 이미 패치가 나와 있던 것**이었다. 고객 약 15만 7천 명의 정보가 새고(1만 5천여 명은 계좌 정보까지) 사고 비용은 약 4,200만 파운드였다. 규제기관의 총평은 짧았다 — *"가장 기본적인 보안 조치조차 하지 않았다."* 2008년 미국 결제회사 Heartland 는 같은 공격으로 카드번호 약 1억 3천만 장이 털렸다. 교훈은 하나다 — **대부분의 큰 사고는 새로운 마법이 아니라 오래전에 답이 나온 기본을 안 지켜서 벌어진다.**

**개인정보 최소 원칙.** 개인정보(PII)는 자산이자 책임이다. 지킬 것 넷 — ① **필요한 것만 모은다**(한국 개인정보보호법도 "목적에 필요한 최소한만"으로 정한다). ② **비밀번호는 절대 그대로 저장하지 않고** 빠른 해시가 아닌 bcrypt·Argon2 같은 비밀번호 전용 방식을 쓴다. ③ **민감정보(주민번호·카드번호)는 직접 다루지 않는 게 최선** — 결제는 PG 에, 본인확인은 인증 서비스에 맡긴다. ④ **밝힌 목적에만 쓴다.** 한 줄 요약은 **"덜 모으고, 비밀번호는 해시하고, 민감정보는 남에게 맡기고, 목적 밖으로 쓰지 않는다"** — 모으지 않은 정보는 유출될 수도 없으니 **가장 안전한 데이터는 애초에 안 가진 데이터**다. 실제 사용자를 받는다면 가입 시 수집·이용 동의를 받고, 개인정보처리방침 한 장을 두고, 제3자 제공 시 다섯 가지(제공받는 자·이용 목적·제공 항목·보유 기간·거부권과 불이익)를 밝혀야 한다.

**백업과 참사들.** 해커가 없어도 데이터는 실수 한 번으로 사라진다. **픽사 「토이 스토리 2」(1998년 제작 중)** — 잘못된 명령으로 영화 파일이 눈앞에서 지워지기 시작했고 백업 시스템도 한 달째 고장 나 있었다. 영화를 살린 건 출산 후 재택근무하던 기술 총괄이 집 컴퓨터에 둔 2주 전 사본이었다. **GitLab(2017)** — 실수로 잘못된 서버의 데이터를 지웠는데 여러 겹의 백업이 모두 조용히 고장 나 있어 6시간치를 잃었다. **Ma.gnolia(2009)** — 백업을 원본과 같은 시스템에 뒀다가 함께 사라져 서비스가 문을 닫았다.

교훈은 **3-2-1 규칙**(CISA 권고)으로 정리된다 — **3벌**(원본 1 + 사본 2) · **2종**(서로 다른 매체) · **1벌은 다른 장소에**(화재·도난·랜섬웨어 대비). 개인 실천 예는 노트북 원본 + 외장하드 사본 + 클라우드 한 벌이다. 그리고 CISA 가 특히 강조하는 것 — **복구가 진짜 되는지 가끔 확인하라. 열어본 적 없는 백업은 백업이 아니다.** 참고로 클라우드 DB 무료 요금제에는 자동 백업이 없는 경우가 많다(Supabase 무료는 직접 백업 필요, 자동 일일 백업은 Pro 부터).

### 6. 무료로 쓸 수 있는 DB 고르기
비전공자도 무료로 진짜 DB 를 쓸 수 있지만 전제가 하나 있다 — **무료 티어는 배우기·MVP 용이지 큰 규모의 운영용이 아니다.** 강의는 2026-02 기준 공식 가격 페이지를 확인해 비교한다.

| 서비스 | 종류 | 확인한 점 | 비전공자에게 |
|---|---|---|---|
| Supabase | PostgreSQL | DB 500MB · 스토리지 1GB, **자동 백업 미포함**, 1주 미사용 시 일시정지 | 로그인·파일까지 한 번에 실습할 때 |
| Neon | PostgreSQL | 개발·프로토타이핑용, 유휴 컴퓨트 scale-to-zero | 순수 Postgres·브랜치를 써 볼 때 |
| Turso | SQLite | DB 100개 · 5GB, 월 읽기 5억 행 · 쓰기 1천만 행 | SQLite 기반 가벼운 서비스 실험 |
| PlanetScale | Postgres/Vitess | 시작 요금 월 $5부터 — 무료 티어 표에서 제외 | 무료가 조건이면 다른 후보부터 |

**내 컴퓨터에 직접 설치**하는 무료 길도 있다. **SQLite** 는 DB 전체가 **파일 하나**라 서버를 따로 켤 필요 없이 앱이 직접 읽고 써서 작은 앱·프로토타입에 좋다(많은 도구에 기본 내장). **PostgreSQL · MySQL** 은 회사들이 실제로 쓰는 오픈소스를 내 컴퓨터에 무료로 설치하는 것이고, 설치가 번거로우면 **Docker** 로 명령 한 줄에 띄웠다 통째로 지울 수 있다. 로컬은 완전 무료·오프라인·내 손안이라 개발과 학습에 최고지만 남에게 열려면 배포나 터널이 필요하고 컴퓨터가 꺼지면 멈춘다. 그래서 흔한 흐름은 **"로컬에서 만들고 → 세상에 낼 때 클라우드로"** 다.

가입 전 확인할 것 다섯 — 용량 한도, 미사용 시 일시정지, 백업 방법(자동 백업 포함 요금제인지), 정책 변경 가능성, 트래픽 증가 시 유료 전환(요금·용량 알림 켜기).

AI 에게 DB 를 붙여 달라고 할 때의 프롬프트도 제시된다 — ① 저장할 것을 말하고 스키마 제안받기 ② 무료 SQL DB 기준 생성 방법 ③ **접속 정보는 환경변수로** ④ **파라미터화 쿼리 + 비밀번호 해시**. ③·④ 는 지난 시간의 환경변수·보안, 오늘의 SQL 주입 방어와 그대로 이어진다.

### 7. 실습 — 에이전트로 '내 Todo 앱' 만들기
배운 걸 모아 **내 컴퓨터에서 도는 Todo 앱**을 만든다. 할 일을 추가·확인·완료·삭제하고 그 데이터가 무료 DB 에 저장돼 껐다 켜도 남는다 — Todo 앱은 **CRUD 의 교과서**라 DB 를 손에 익히기에 딱이다. 방식은 에이전틱으로, 목표(PRD)를 주면 에이전트가 계획·설치·구현을 하고 사람은 검토·판단·수정한다.

**1부 — PRD 와 DB 설계.** 무엇/기본 기능(CRUD)/저장/내가 넣고 싶은 기능(마감일·태그·검색 등)/규칙(무료 도구만, 비밀값은 `.env`)을 한 장으로 적고, **구현 전에 DB 구조부터 설계받는다.** "표·열·관계를 구조도로 그려 보여 줘"라고 요청해 앞서 배운 관계대로 잡혔는지 눈으로 확인한다(태그를 넣었다면 `todos` ↔ `tags` 를 잇는 연결표 `todo_tags` 가 나오는 다대다 구조).

**2부 — 길 A(로컬).** 합의한 구조로 SQLite 파일 하나(`todo.db`)에 저장하고 브라우저 `localhost` 로 열리게 만든다. `.env` 와 `todo.db` 는 `.gitignore` 에 넣는다. 사람이 할 일은 셋 — **계획 한 번 읽기 · 위험한 명령 승인(프로젝트 폴더 안인지 확인) · 잘 되던 순간마다 Git 커밋.** 통과 기준은 새로고침·재시작 후에도 남고 DB 뷰어로 `todos` 표에 행이 실제로 쌓였는지 확인하는 것이다.

자주 막히는 곳도 표로 정리된다 — `better-sqlite3` 빌드 에러(네이티브 모듈이라 OS별 빌드 도구 필요), 포트 충돌(EADDRINUSE), **"추가했는데 새로고침하면 사라짐"**(화면에만 있고 DB 엔 안 들어감), 코드 수정 미반영(개발 서버 재시작, 특히 `.env` 수정 후), `todo.db` 를 GitHub 에 올려버림(`.gitignore` 추가 + 이미 커밋했다면 git 이력에서도 제거). 안 되면 에러를 그대로 에이전트에 붙여넣어 고치게 하고, 계속 못 고치면 마지막으로 되던 지점으로 되돌려 문제를 잘게 쪼갠다.

**3부 — 길 B(클라우드).** 같은 앱을 Supabase 로 바꿔 남에게 링크로 보여줄 수 있게 한다. 접속 키는 `.env` 로 빼고 **RLS(행 수준 보안)를 반드시 켠다** — 안 켜면 공개 키로 누구나 데이터에 접근할 수 있다.

### 8. 마무리 — 회고와 핵심 정리
회고 질문 네 개가 주어진다 — DB 가 도서관/마법 장난감 상자와 어떻게 닮았는지 한 문장으로, `SELECT … FROM … WHERE …` 를 내 서비스 예로 바꿔 말로 풀어 보기, "Little Bobby Tables"가 내 서비스에서 일어나지 않게 하려면 AI 에게 무엇을 요구할지, 백업 참사 중 가장 섬뜩했던 것과 나의 예방책.

| 오늘 배운 것 | 한 문장 정리 | 내가 할 수 있는 행동 |
|---|---|---|
| DB 의 역할 | 서비스의 '기억' — 데이터를 남기고 빠르게 찾아 준다 | 새로고침해도 남아야 할 데이터를 구분한다 |
| 역사와 갈래 | 파일 → SQL → NoSQL(4종) → 클라우드 | 표(SQL)와 유연한 상자(NoSQL)의 성격을 안다 |
| SQL 알아보기 | 거의 영어 문장이며 코드는 AI 가 쓴다 | `SELECT … FROM … WHERE …` 를 말로 푼다 |
| 보안·백업 | 주입은 파라미터화로 막고 데이터는 백업으로 지킨다 | AI 에게 파라미터화·해시·자동 백업을 요구한다 |
| 무료 DB | 무료 티어로 시작하되 한도·백업·정책을 안다 | 첫 서비스엔 Supabase(Postgres)를 후보로 둔다 |

## 느낀 점 / 적용할 점
- 오늘 배운 것이 마침 진행 중인 [saju_tarot](../../saju_tarot) 에 거의 그대로 들어 있어서 이해가 빨랐다. `storage.py` 의 `readings` · `share_links` 두 표가 **1:N**(리포트 1건 ↔ 공유 링크 여러 개)이라 `share_links` 에 `reading_id` 칸 하나만 있고, `REFERENCES readings(id)` 가 강의에서 말한 **키**였다. 공유 링크가 리포트 내용을 베끼지 않고 번호로만 가리키는 것이 **정규화**이고, 만료 정리용·공유 조회용으로 딱 두 개만 걸어 둔 인덱스가 "자주 쓰는 곳에만 최소한"이라는 원칙 그대로였다.
- 강의의 SQL 주입 방어(파라미터화 쿼리)와 개인정보 최소 원칙도 이미 적용돼 있었다 — 이름·생년월일은 암호화해 저장하고, 공유 링크로 나갈 때는 생년월일시를 빼서 내보낸다. "가장 안전한 데이터는 애초에 안 가진 데이터"라는 문장이, 공유 응답에서 개인 식별 값을 걷어내는 코드와 정확히 같은 이야기였다.
- 반면 **백업은 전혀 안 되어 있다**는 걸 오늘 알았다. SQLite 파일 하나에 실제 이용자의 이름·생년월일이 쌓이고 있는데 사본이 한 벌도 없다. 3-2-1 규칙에서 3벌·2종·off-site 1벌 중 지켜진 게 없는 셈이다. 픽사와 GitLab 사고의 공통점이 "있다고 믿었지만 고장 나 있었다"인데, 나는 아예 없는 쪽이라 더 위험하다 — 정기 사본부터 만들어야겠다.
- 무료 DB 비교에서 Supabase 무료 요금제에 **자동 백업이 없고 1주 미사용 시 일시정지**된다는 점이 특히 눈에 띄었다. 클라우드에 올리면 자동으로 안전해질 거라 막연히 생각했는데, 요금제에 따라 백업은 여전히 내 몫이라는 걸 확인했다.
- 마이그레이션 항목의 경고("칸을 삭제하는 변경은 데이터가 영구히 사라질 수 있으니 구조 변경 전엔 반드시 백업")는 앞으로 DB 구조를 바꿀 때마다 떠올려야 할 문장이다. 지금까지는 구조를 바꾸는 걸 코드 수정과 같은 무게로 여겼는데, 되돌릴 수 없는 작업이라는 점에서 성격이 다르다.
