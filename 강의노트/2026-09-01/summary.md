# 바이브 코딩으로 웹 만들기 — 웹의 세 겹, CS 기초, AI로 게임 만들기

## 핵심 요약
- 웹페이지는 구조(HTML)·표현(CSS)·동작(JavaScript) 세 겹으로 이루어지며, 각 층은 서로 다른 시대에 서로 다른 문제를 풀기 위해 태어났다(HTML: 흩어진 문서 연결, CSS: 내용과 꾸밈 분리, JS: 정적인 문서에 반응 부여).
- AI에게 화면 작업을 시킬 때 이 세 겹 중 어디를 고칠지 지정해서 요청하면 AI가 손댈 범위가 좁아지고 결과 검증도 쉬워진다.
- JavaScript는 싱글 스레드로 동작하기 때문에, 오래 걸리는 작업은 동기가 아니라 비동기(이벤트 루프)로 처리해 화면이 멈추지 않게 만든다.
- 브라우저는 탭마다 프로세스를 분리(멀티프로세스)해 안정성을 높이고, 그 안에서 여러 스레드가 협력하며, 물리적 코어 수보다 훨씬 많은 스레드를 시분할로 처리한다.
- 실습으로는 채팅형 AI에 "테트리스 만들어줘" 한 줄로 게임을 만들어보고(1차), 이어서 규칙을 직접 적어 나만의 게임을 개발 에이전트로 만든 뒤(2차) GitHub Pages로 배포해 링크를 제출하는 과제까지 이어진다.

## 상세 내용

### 1. AI는 잘 만드는데, 내 말은 왜 안 통할까 — 웹의 세 겹
웹페이지는 화면에 무엇이 있는지(구조), 어떻게 보이는지(표현), 사용자가 뭔가 했을 때 무엇이 바뀌는지(동작)라는 세 가지 질문으로 나뉘고, 이를 각각 HTML·CSS·JavaScript가 담당한다. HTML은 `<h1>`, `<button>` 같은 태그로 정보에 의미를 붙이고, CSS는 `color`, `text-align` 같은 규칙으로 보이는 방식을 정하며, JavaScript는 `addEventListener` 같은 코드로 클릭 등 사용자 행동에 대한 반응을 만든다. 이 세 겹을 구분해서 AI에게 요청하면("모바일에서도 읽히게 간격을 조정해줘" 등) 결과를 검증할 기준도 명확해진다. 안내 문구 문제는 HTML, 모바일에서 카드가 겹치는 문제는 CSS, 버튼이 반응 없는 문제는 JavaScript에 속한다는 진단 연습으로 마무리된다.

### 2. 세 겹을 나누어 이해하기 — 이름에 담긴 사연
HTML은 1989년 CERN의 팀 버너스리가 흩어진 연구 문서를 서로 연결하기 위해 제안한 하이퍼텍스트(HyperText Markup Language)에서 나왔고, 1993년 CERN이 로열티 없이 공개한 덕분에 모두의 기반이 되었다. CSS는 내용과 꾸밈이 한 덩어리로 붙어 있어 "제목 색을 전부 바꿔주세요" 같은 요청마다 모든 문서를 일일이 고쳐야 했던 문제를 풀기 위해 1994년 호콘 비움 리가 제안했고, 이름의 '캐스케이딩'은 여러 스타일 규칙이 폭포처럼 층을 이루며 우선순위를 갖는다는 뜻이다. JavaScript는 1995년 넷스케이프의 브렌던 아이크가 열흘 만에 만든 언어로, 처음 임무는 폼 검증이었고, 10년 뒤 구글 지도의 등장(AJAX)으로 웹이 '문서'에서 '애플리케이션'으로 넘어가는 전환점을 만들었다. 이 구분은 데이크스트라의 '관심사의 분리' 원칙이 웹 설계에 적용된 결과이며, 협업에서도 콘텐츠·디자인·개발 담당자가 각자의 겹을 맡는 구조로 이어진다. 이 강의는 프론트엔드(브라우저에서 보이는 HTML/CSS/JS)와 백엔드(서버의 저장·처리·권한)의 구분도 함께 소개한다.

### 3. [오늘의 CS] 동기·비동기, 프로세스·스레드·코어
동기는 전화처럼 끝날 때까지 기다리는 방식이고, 비동기는 문자처럼 보내두고 다른 일을 하다가 응답이 오면 처리하는 방식이다. JavaScript는 한 번에 한 가지 일만 하는 싱글 스레드 언어라서, 오래 걸리는 작업(fetch, setTimeout)을 동기로 처리하면 화면 전체가 멈춘다. 그래서 이런 작업은 비동기로 걸어두고, 완료되면 이벤트 루프가 결과를 대기줄에서 꺼내 처리한다. 한편 프로세스는 독립된 메모리를 쓰는 실행 단위이고 스레드는 그 안에서 메모리를 공유하며 일하는 단위인데, 크롬은 2008년 탭마다 프로세스를 분리하는 설계를 도입해 한 탭의 오류가 브라우저 전체를 끌고 넘어지지 않게 만들었다. 코어는 실제 계산을 하는 물리적 단위이며, 코어 수보다 훨씬 많은 프로세스·스레드는 운영체제가 초고속으로 번갈아 실행하는 시분할 방식으로 처리된다.

### 4. AI로 게임 만들기 — 테트리스에서 내 게임까지
1차 실습은 웹 채팅형 AI에 "테트리스 만들어줘" 한 줄만 입력하는 것으로, 테트리스는 전 세계가 공유하는 게임이라 이름 자체가 규칙 명세서 역할을 해 한 줄 요청만으로도 동작하는 게임이 나온다. 결과물의 코드 보기에서 HTML(게임판·점수 표시), CSS(`<style>` 태그의 색과 배치), JavaScript(`<script>` 태그의 키 입력·블록 낙하·줄 삭제)가 각각 어디 있는지 확인하는 관찰이 이어진다. 2차 실습은 방향이 반대로, 이름만으로는 규칙이 전달되지 않는 '나만의 게임'을 직접 설계해 개발 에이전트(Claude Code 등)로 만든다. 모든 게임은 보이는 것(화면 요소)·상태(진행 상황)·규칙(행동에 따른 변화)이라는 세 재료로 분해할 수 있으며, 이 표를 먼저 채운 뒤 화면·상태·규칙을 구체적으로 적어 요청문을 작성하고, index.html/styles.css/script.js 세 파일로 나눠 만들도록 안내한다.

### 6. 과제 — 나만의 게임을 웹에 올리고 링크 제출하기
완성한 게임을 GitHub Pages로 배포해 `https://내아이디.github.io/저장소이름/` 형태의 링크로 누구나 열어볼 수 있게 만드는 과제다. 개발 에이전트에게 "이 폴더를 깃 저장소로 만들고 GitHub에 새 공개 저장소로 올린 뒤 Pages를 켜달라"고 요청하되, 로그인·권한 승인처럼 사람이 직접 해야 하는 단계는 AI가 멈추고 안내하도록 요청한다. 제출 전 체크리스트로 새 창(시크릿 창)에서 링크가 열리는지, 실제 웹 주소에서 조작이 동작하는지, 휴대폰에서도 플레이되는지, 동료에게 링크를 보내도 열리는지를 확인한다.

## 느낀 점 / 적용할 점
- 오늘 배운 "세 겹으로 나눠 진단하기"는 AI에게 프론트엔드 수정을 요청할 때 바로 적용할 수 있는 실전 습관이다 — 문제가 구조/표현/동작 중 어디인지 먼저 판단한 뒤 그 층의 언어로 구체적으로 요청하기.
- 비동기·이벤트 루프 개념은 실제로 `ksk_game` 저장소의 index.html 같은 게임 코드에서 setTimeout, requestAnimationFrame 같은 패턴을 만날 때 바로 적용해볼 수 있다.
