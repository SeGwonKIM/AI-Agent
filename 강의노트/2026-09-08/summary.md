# 다 만들려 하지 말고 — 범위를 좁히고 다섯 단계로 '굴러가는 첫 조각'까지

## 핵심 요약
- **오늘의 목표는 '완성'이 아니라 '굴러가는 첫 조각'이다.** 초보 프로젝트가 실패하는 이유는 기능이 너무 적어서가 아니라 **너무 많아서**다. 그래서 한 문장으로 좁히고 → 다섯 단계로 한 걸음씩 → 막히면 되돌리며 간다. 리드 호프먼의 말이 기준선이다 — *"첫 버전이 부끄럽지 않다면 너무 늦게 낸 것이다."*
- **MVP는 '축소판'이 아니라 '하나는 끝까지 되는 것'이다.** 목표가 이동이라면 **스케이트보드는 MVP지만 자동차 타이어 하나는 MVP가 아니다** — 타이어로는 아무 데도 못 간다. 기능 수가 아니라 **사용자 흐름의 완결성**이 기준이다. 에어비앤비는 거실에 에어매트리스 3개, 드롭박스는 제품 없이 3분 영상, 인스타그램은 기능 잔뜩이던 Burbn에서 사진만 남긴 것이 시작이었다.
- **'안 만들 것' 목록이 비밀 무기다.** MoSCoW(꼭/있으면 좋음/나중에/**지금은 안 함**)로 나누고 MVP에서는 Must만 만든다. Won't 를 **일부러 5개 이상** 적어 두면 스코프 크립(기능이 슬금슬금 느는 것)을 막는다. 무서운 건 스코프 크립이 **진보처럼 느껴진다**는 점이다 — 하나하나는 다 그럴듯하다("고객이 원해서", "경쟁사에 있어서", "하루면 된다길래").
- **다섯 단계 절차: PRD → 작업대(하네스) → 화면 → 저장+규칙 → 한 바퀴+배포.** 명령은 **'무엇을'로만** 준다. "어떤 DB를 써라", "이 방식으로 막아라" 같은 **방법(how)은 AI 몫**이고, 나는 **의도**와 **됐는지 확인**에만 집중한다. 오늘의 진짜 산은 4단계 — **정원 초과 방지**다. 브라우저에서 "남은 자리 세고 → 신청 넣기"는 동시에 누르면 뚫린다. `현재 신청 수 < 정원`을 조건으로 한 **DB 안의 단일 원자적 저장**이어야 마지막 한 자리에 열 명이 몰려도 딱 한 명만 성공한다.
- **막혔을 때의 네 가지 규율: ① 한 번에 하나만 ② 작동하면 저장(커밋) ③ 막히면 되돌리고 리셋 ④ 이해 못 한 코드는 배포하지 않는다.** 특히 **둠 루프**(거의 다 됐는데 안 잡히고, 프롬프트를 더 넣을수록 멀쩡한 기능까지 깨지는 상황)는 운이 아니라 구조적이다 — 대화가 길어지며 맥락이 오염되고, AI에겐 의존 관계 지도가 없어 원인이 아니라 증상만 땜질하기 때문이다. **막힘이 30분을 넘기면 더 파기 전에 되돌리는 것이 대개 더 빠르다.**

## 상세 내용

### 1. 오늘 쓰는 다섯 가지 재료 — 지금까지 배운 조각을 꿴다

오늘은 흩어져 배운 것을 하나로 모으는 날이다. 재료는 다섯 가지다.

| 재료 | 역할 |
|---|---|
| PRD | 무엇을 만들지 정하는 **한 장** |
| 하네스 | 어디서 만들지 정하는 **작업대** |
| HTML·CSS·JS + 목업 데이터 | 화면을 그리는 **세 겹** |
| 서버+DB 또는 Supabase, `.env` | 저장을 붙이는 곳과 **비밀값 관리** |
| 배포 | 내 컴퓨터에서만 보이던 것을 **인터넷 주소로** |

오늘 계속 쓰는 말도 미리 한 줄로 잡아 뒀다.

- **PRD** — 무엇을·왜 만들지 정리한 기획서 한 장
- **MVP** — 사용자가 핵심 결과 하나를 끝까지 얻을 수 있는 최소 작동 버전
- **목업 데이터** — 진짜처럼 보이는 가짜 데이터 (저장 없이 화면부터 채우는 용도)
- **CRUD** — 데이터 만들기·읽기·고치기·지우기
- **하네스** — AI 코딩을 실행·검토하는 작업 환경 (브라우저형·편집기형·터미널형)
- **환경변수(`.env`)** — 비밀값을 코드 밖에 보관하는 자리
- **커밋** — 지금 작동하는 상태에 이름을 붙여 **복구 지점**을 만드는 기록
- **배포** — 내 컴퓨터에서만 보이던 것을 누구나 들어오는 주소로 내보내기

**착수 순간부터 제출 기준을 본다** — 이게 프로답게 범위를 잡는 첫걸음이라고 했다. 메인 퀘스트 01의 제출물은 실행 가능한 웹 서비스(저장소 또는 배포 URL) · 기획 문서 1장 · 회고록 1장 · 3분 이내 시연 영상이고, 평가는 도메인 연결성 25% · 기능 완성도 25% · AI 활용도 20% · 회고 깊이 15% · 발표/시연 15% 다.

눈에 띈 건 **AI 활용도 20%** 의 증거가 "AI와 주고받은 대화 — **지우지 말고 그대로 남기기**"라는 점이다. 대화 로그 자체가 제출물이 된다.

### 2. 범위 좁히기 — MVP는 스케이트보드다

MVP는 "완성품의 축소판"도 "화면만 그럴듯한 시제품"도 아니다. 사용자가 **의미 있는 한 가지 일을 처음부터 끝까지** 해낼 수 있는, **의도적으로 작은** 버전이다.

목표가 "이동"이라면 스케이트보드는 훌륭한 MVP다. 느려도 실제로 굴러가고 나를 데려다준다. 반면 **자동차 타이어 하나는 MVP가 아니다** — 그걸로는 아무 데도 못 가니까. 그래서 기준은 기능 수가 아니라 **흐름의 완결성**이다.

#### 거대한 앱도 시작은 초라했다

- **에어비앤비(2007)** — 창업자들이 자기 집 거실에 에어매트리스 3개를 깔고, 사진 몇 장과 허름한 웹페이지 하나로 시작. 예약 시스템도, 리뷰도, 결제도 없었다. 첫 주말 손님 3명이 80달러씩 냈고, 그걸로 **"낯선 사람이 낯선 집에 돈 내고 묵을까?"** 라는 가장 큰 의문을 검증했다.
- **드롭박스** — 아예 제품을 안 만들고 3분짜리 시연 영상만 올렸다. 대기자가 하룻밤에 5천 → 7만 5천 명. **만들기 전에 수요를 확인한 것.**
- **인스타그램** — 체크인·일정 기능이 잔뜩 든 'Burbn'이었는데, 사용자들이 **사진 공유만 특히 많이 쓴다**는 걸 보고 사진·필터·피드로 좁혔다. 2년 만에 10억 달러에 팔렸다.

#### 실패에서 방향을 튼 회사들 — 피벗

작게 시작하는 것만큼 중요한 게 **안 되는 건 빨리 접고 방향을 트는 것**이다.

- **슬랙** — 원래 「Glitch」라는 온라인 게임 회사. 게임은 안 됐지만 팀이 자기들끼리 쓰려고 만든 **사내 채팅 도구**가 진짜였다. 게임을 접고 그걸 제품으로 낸 게 슬랙(훗날 세일즈포스에 약 277억 달러 인수).
- **트위터** — 원래 팟캐스트 회사(Odeo). 애플이 아이튠즈에 팟캐스트를 넣자 하루아침에 설 자리를 잃었고, 위기 속 사내 아이디어 "140자 짧은 글"이 트위터가 됐다.

공통점 하나 — **"내가 부수적으로 만든 것"이 진짜 제품이었다.** 만들다가 "어? 이 부분이 진짜 쓸 만한데?" 싶으면 원래 계획을 고집하지 말라는 것. 시스트롬의 말처럼 "최고의 회사들에는 모두 전신(前身)이 있었다."

#### 자를 용기 — 테스트 하나면 된다

> **"이 기능 없이 출시해도, 사용자가 핵심 문제를 풀 수 있나?"** → 그렇다면(또는 애매하면) **자른다.** 버전 2에 넣으면 된다.

단, 반대쪽 함정도 있다 — **너무 잘라서 "사용자가 원한 결과를 하나도 끝낼 수 없다면" 그건 지나치게 자른 것**이다.

#### 기능을 더하다 가라앉은 배들

- **경쟁사 따라하기** — 경쟁사가 냈다는 이유로 3주 만에 급조했는데 미완성·버그투성이라 지원 요청만 쌓였고, 정작 그 기능을 원하던 고객은 경쟁사로 갔다.
- **"다 들어드릴게요"의 함정** — 잘나가던 간단한 뉴스레터 도구가 고객 요청마다 소셜 예약·CRM·고급 분석을 붙이다 **뭐 하나 제대로 못 하는 도구**가 됐다.
- **큰 회사도** — 윈도우 비스타, 초기 아이튠즈가 "한꺼번에 다 개선"하려다 무겁고 느려진 사례.

> 성공한 제품은 **"무엇을 만들었나"만큼 "무엇을 거절했나"** 로 정의된다.

#### 한 문장으로 정의하기

좋은 정의는 **'어떻게 만들지(해결책)'가 아니라 '누구의 어떤 불편(문제)'** 에 초점을 둔다.

> **[누가]** 가 **[어떤 상황/언제]** 에 **[무엇을 못 해서]**, **[어떤 불편]** 을 겪는다.

예: *"동네 카페 단골손님이 재방문할 때 종이 쿠폰을 자주 잃어버려서, 사장님도 손님도 적립 혜택을 놓친다."* — 누가·언제·무엇·불편이 다 담기고 **해결책은 열려 있다.**

점검 질문은 하나다 — **"사용자가 가치를 얻으려면 완료해야 하는 단 하나의 행동은 무엇인가?"** 이걸 한 문장으로 못 쓰면 범위가 아직 넓다는 신호다. 그리고 사용자를 '모두'로 두지 말고 **첫 버전에서 가장 득을 볼 한 사람**('사장님' 말고 '재방문 단골')으로 콕 집는다. 문장에 "앱으로·자동으로·AI로" 같은 **수단이 들어 있으면 빼서 문제만 남긴다.**

#### 도메인별 '첫 조각' 예시

| 누구 | 욕심내면 (버전2로) | 첫 조각 (딱 이것 하나) |
|---|---|---|
| 카페 사장 | 스탬프 적립 + 등급/포인트 + 쿠폰 발송 + 매출 통계 | 메뉴를 보여주는 한 화면 |
| 병원 행정 | 제증명 온라인 신청 + 결제 + 발급 + 예약 연동 | 서류 목록 + 각 서류 설명 한 화면 |
| 독서모임 운영자 | 회원관리 + 출석 + 토론 게시판 + 도서 추천 | 다음 모임 날짜·장소·읽을 책 한 화면 |
| 헬스 트레이너 | 회원별 기록 + 식단 + 결제 + 채팅 상담 | 오늘의 운동 루틴을 순서대로 보여주는 화면 |
| 프리랜서 | 청구서 + 결제추적 + 자동 리마인더 + 다국어 | 청구서 1장 만들어 보내는 흐름 하나 |

#### 범위 정하기 워크북

| 항목 | 채울 것 |
|---|---|
| 한 문장 설명 | 한 문장에 안 담기면 범위가 너무 넓다 |
| 핵심 흐름 하나 | 사용자가 처음부터 끝까지 하는 한 가지 |
| 꼭(Must) 3개 | 그 흐름에 반드시 필요한 것 |
| 지금은 안 함(Won't) 5개 | 이번엔 **일부러** 빼는 것 |
| 완성 기준(done) | "이것까지 되면 오늘 성공" 한 줄 |

**완성 기준과 마감을 먼저 정하고 거기에 범위를 맞춘다.** 범위에 마감을 맞추면 끝없이 늘어난다.

### 3. 실전 기록 — 에이전트와 대화로 스펙부터 배포·관리자까지

다섯 단계를 직접 밟기 전에 전체가 **에이전트와의 대화로 어떻게 굴러가는지** 크게 한 번 봤다. 네 걸음이다.

**1) 스펙부터 — 코드보다 문서를 먼저.** 바로 "만들어 줘"라고 하면 에이전트는 그럴듯한 코드를 쏟아내지만 **정원 초과 금지 같은 내 규칙이 슬쩍 빠진다.** 그래서 어제 배운 스펙 주도 방식을 쓴다. PRD가 '무엇을'이라면, **OpenSpec** 은 그걸 도구로 정형화해 제안·설계·명세·작업목록으로 나눠 주는 심화판이다(필수는 아니다).

```
npm install -g @fission-ai/openspec@latest
openspec init
```

Claude Code 에서는 슬래시 명령으로 흐른다: `/opsx:explore`(요구 정리) → `/opsx:propose`(change 문서 일괄 생성) → `/opsx:update`(계획 수정) → `/opsx:apply`(구현) → `/opsx:sync`(메인 명세 반영) → `/opsx:archive`(보관). 일을 **change(변경 제안) 단위**로 다뤄 무엇을·왜(proposal) / 어떻게(design) / 할 일(tasks)을 먼저 문서로 만들고 **사람이 검토한 뒤** 구현한다. `opsx` 는 실험적 워크플로라 명령이 바뀔 수 있다.

여기서 인상적인 원칙이 하나 나왔다 — **PRD에는 기술 선택을 넣지 않는다(무엇을 만들지는 사람이 정한다). 대신 스택은 AI가 후보를 견줘 고르고, 그 근거를 설계 문서에 남기게 한다.**

**2) Supabase를 에이전트에 직접 연결.** MCP로 붙이면 에이전트가 내 Supabase에 직접 표·정책·함수를 만든다.

```
claude mcp add --scope project --transport http supabase "https://mcp.supabase.com/mcp?project_ref=<내 프로젝트 ref>"
```

여기서 어제 배운 두 가지가 실제로 쓰인다.

- **정원 초과 방지는 화면이 아니라 DB 안에서.** 브라우저에서 남은 자리를 세고 신청을 넣는 방식은 여러 명이 동시에 누르면 뚫린다. `현재 신청 수 < 정원`을 조건으로 한 **단일 원자적 저장을 DB 함수**로 만들고, 신청은 무조건 그 함수를 거치게 한다.
- **행 수준 보안(RLS).** 표에 RLS를 켜고 '본인 신청만 조회' 정책을 걸면 로그인해도 남의 신청은 못 본다.

**확인은 눈으로** — 마지막 한 자리를 두고 서로 다른 계정으로 동시에 신청해 **딱 한 건만 성공**하는지 로그로 본다.

**3) 배포와 관리자.** 정적 화면은 GitHub Pages로 (배포물에는 **공개 키만**). 관리자 페이지에서 중요한 건 — **화면에서 버튼만 숨기기는 보안이 아니다.** 누구든 요청을 직접 보낼 수 있으니까. 관리자 명단을 DB에 두고, 관리용 함수가 실행될 때마다 스스로 '관리자냐'를 다시 확인하게 만든다. **화면은 패널을 보여 줄 뿐, 진짜 문지기는 DB다.**

#### 심화 — 데모를 '진짜 서비스'로 올리려면

당장 다 할 필요는 없고 체크리스트로 채워 갈 것들이다.

- **비밀 키 재발급과 서버 전용 보관** — 서비스 롤(secret) 키가 한 번이라도 새어 나갔다면 즉시 재발급. **이 키 하나로 접근 제어가 통째로 우회된다.**
- **이메일 확인 켜기 + 커스텀 SMTP** — 확인을 끄면 남의 이메일로도 무제한 가입된다.
- **비밀번호 정책과 유출 검사** — 길이·복잡도 + 이미 유출된 비밀번호 차단(HaveIBeenPwned 연동).
- **남용 방어** — CAPTCHA와 요청 제한(rate limit).
- **접근 제어 재점검** — 모든 표에 RLS, 보안 점검 도구(advisor) 주기적 실행.
- **도메인·주소 설정** — 자체 도메인·HTTPS, 로그인 뒤 돌아올 Site URL과 허용 목록.
- **운영 기본기** — 백업, 로그·모니터링, 개인정보 보관·파기 정책.
- **무료 티어의 한계** — 콜드 스타트, 용량·발송 한도.

### 4. 따라하며 익히기 — 정원 있는 '원데이 클래스 신청'을 5단계로

목표 문장은 이랬다. *"정원 10명짜리 원데이 클래스에 이름으로 신청받고, 남은 자리를 보여주다가, 정원이 차면 '마감'을 띄운다. 신청은 새로고침해도 남고, 여러 명이 동시에 눌러도 정원을 넘기지 않는다."* — 로그인·결제·후기는 **만들지 않는다.**

| 단계 | 하는 일 | 통과하면 생기는 것 |
|---|---|---|
| 1. PRD | 만들 것을 한 장으로 | AI에게 줄 설계도 |
| 2. 작업대 | 하네스 고르고 빈 프로젝트 세우기 | 내 화면에 프로젝트가 뜬다 |
| 3. 화면 | 눈에 보이게 만들기 | 클래스와 남은 자리가 진짜처럼 보인다 |
| 4. 저장 + 정원 | 신청을 저장하고 정원을 지키게 | 신청이 남고, 정원을 넘지 않는다 |
| 5. 한 바퀴 + 내보내기 | 처음부터 끝까지 돌리고 배포 | 누구나 드는 신청 주소가 생긴다 |

핵심은 **명령을 '무엇을'로 준다**는 것. 방법(how)은 AI가 정할 몫이고, 나는 **의도**와 **됐는지 확인**에 집중한다. 그래서 단계마다 세 가지가 붙어 있다 — **명령(의도만) / 확인(직접 눈으로) / 막히면(다시 지시).**

#### 1단계 PRD

```
mkdir class-signup
cd class-signup
claude
```

명령을 한 줄에 하나씩 적은 이유가 나왔다 — **`&&` 같은 연결자는 터미널 종류마다 다르게 동작한다**(윈도우 PowerShell 5, cmd, 맥·리눅스 셸이 제각각). 한 줄씩 실행하면 어디서든 똑같이 된다.

PRD 본문은 이런 모양이다. **스택·구조는 정하지 않는다.**

```
[무엇] 정원이 정해진 '원데이 클래스' 신청 페이지.
[기능] 클래스 정보(제목·일시·정원)와 남은 자리를 보여준다 / 이름을 넣고 '신청'을 누른다.
[동작] 신청은 새로고침해도 남는다. 정원이 차면 더 받지 않고 '마감'을 보여준다.
       여러 명이 거의 동시에 마지막 자리를 눌러도 정원을 넘기지 않는다.
[규칙] 무료 도구만. 비밀값은 코드에 노출하지 않는다. 로그인·결제·후기는 이번엔 만들지 않는다.
```

PRD에서 한 가지 더 정하고 넘어간다 — **누가 쓰는가.** 이 앱은 이름만으로 흐름이 완결되니 로그인은 MVP에서 빼고 '다음 단계'로 계획한다. **빠뜨리는 게 아니라 순서를 정하는 것.** 반대로 사용자 구분이 서비스의 핵심이라면 그때는 미루지 말고 PRD에 넣는다.

**막히면** — AI가 곧장 코드부터 쏟아내거나 계획에 정원 얘기가 빠지면 *"아직 코드는 말고, 무엇을 저장할지와 정원을 어떻게 지킬지부터 계획으로 먼저 보여 줘"* 라고 다시 지시. **코드가 나오기 전에 잡는 게 제일 싸다.**

#### 2단계 작업대 — 하네스 셋

| 하네스 | 생김새 | 언제 좋은가 |
|---|---|---|
| 브라우저형 | 설치 없이 웹에서 코딩·실행 | 아주 처음, 설치가 부담일 때 |
| 편집기형 | Cursor·VS Code + AI | 파일 여러 개를 다루기 시작하면 |
| 터미널형 | 글자로 명령하는 에이전트 (Claude Code) | 설치·실행·배포까지 AI가 스스로 하게 할 때 |

배포까지 갈 거라면 터미널형(Claude Code)을 권한다고 했다. 계획(`/plan`)·구현·실행·검증·커밋이 한자리에서 되기 때문.

#### 3단계 화면 — 저장 없이 목업부터

**눈에 보이는 게 있으면 방향이 맞는지 훨씬 빨리 판단할 수 있다.** 그래서 저장은 아직 없어도 예시 값으로 화면부터 채운다. 버튼을 눌러 반응이 있는지만 보고, 새로고침하면 사라져도 OK.

**한 걸음 더 — 디자인 스킬.** 기본으로 나온 화면은 대개 밋밋하다. 흔한 보라 그라데이션에 기본 폰트, 어디서 본 듯한 카드 — 이른바 **'AI 슬롭'**. 여기서 어제 배운 스킬을 쓴다. Anthropic이 공개한 **`frontend-design`** 스킬이 뻔한 패턴에서 벗어나게 이끌어 준다.

```
/plugin marketplace add anthropics/claude-code
```

명령도 인상적이었다 — *"이 클래스의 분위기(손그림·아늑함)에 맞는 개성 있는 디자인으로, 남은 자리는 숫자만 말고 눈에 보이게. **흔한 AI 티 나는 밋밋한 스타일은 피해 줘**"*. 마음에 안 들면 방향을 한마디로("더 차분하게" / "더 발랄하게") 다시 준다.

#### 4단계 저장 + 정원 — 오늘의 진짜 산

명령(의도만)에 방법이 하나도 없다는 게 핵심이다.

> *"이름을 넣고 '신청'을 누르면 저장돼서 '남은 자리'가 줄고, 새로고침해도 남게 해 줘. 정원이 차면 더 받지 말고 '마감'을 보여줘. 그리고 **여러 명이 거의 동시에 마지막 한 자리를 눌러도 정원을 절대 넘기지 않게** 해 줘. 무료로 시작할 수 있는 방법으로, 비밀값은 코드에 노출되지 않게."*

확인은 넷 다 해야 한다 — ① 신청하면 남은 자리가 즉시 줄고 반영되는가 ② 새로고침해도 남는가 ③ 정원까지 채우면 '마감'이 뜨는가 ④ **동시 신청 테스트에서 딱 한 건만 성공하는가.**

④번 시키는 방법이 좋았다. *"마지막 한 자리를 두고 동시 신청 여러 건을 보내는 간단한 테스트를 만들어 돌려서, 딱 한 건만 성공하고 정원이 10을 넘지 않는지 **로그로 보여 줘**"* — 그리고 **AI 설명만 믿지 말고 눈으로 로그를 확인**하라고 못 박았다.

**막히면** — 11명이 되거나 '마감'이 안 걸리면 그 로그를 그대로 붙여넣고 *"동시에 눌러도 정원을 절대 못 넘기게 **한 번의 원자적 저장**으로 처리해 줘. 지금은 왜 넘치는지도 짚어 줘"*.

#### 5단계 한 바퀴 + 배포

한 바퀴 테스트는 사용자가 되어 **화면 보기 → 신청 → 남은 자리 감소 → 정원까지 채워 마감 확인 → 새로고침해도 유지**를 끝까지. 끊기는 데가 없어야 한다.

배포 확인에서 놓치기 쉬운 게 하나 있었다 — **배포한 주소에서 신청한 뒤 재배포 후 다시 열어도 신청이 남아 있는가.** 서버에 DB를 얹는 무료 배포처는 재시작 시 데이터가 사라지기도 한다. Supabase 같은 외부 DB를 쓰면 그 걱정이 없다.

> **여기까지 못 가도 — 3단계(화면)까지만 해도 오늘은 성공이다.**

### 5. 로그인까지 — Supabase로 회원가입·로그인 붙이기

1단계에서 '다음 단계'로 계획해 둔 그 다음 탈것을 올리는 차례다. 스케이트보드(이름만) 다음의 자전거처럼. 밑바닥부터 만들면 비밀번호 저장·세션·보안을 다 신경 써야 해서 무겁고, 그래서 **Supabase 같은 백엔드 서비스(BaaS)** 에 맡긴다.

순서는 셋이다. ① 무료 프로젝트 만들고 Project URL과 **공개 키**를 `.env` 에 ② 이메일·비밀번호 회원가입·로그인 붙이기 ③ 신청을 로그인한 사용자와 잇고 **RLS로 남의 것은 못 건드리게**.

#### 여기서 막힌다 — 함정 여섯

실제로 붙여 본 사람이 걸린 지점들이라 값이 있었다.

| 함정 | 무슨 일이 나나 | 처방 |
|---|---|---|
| 가짜 이메일 | `test@example.com` 은 `email_address_invalid` 로 막힌다 (없는 도메인 거부) | 실제 받을 수 있는 이메일, 또는 확인 끄기 |
| 가입 직후 로그인 실패 | 기본 설정이 이메일 확인을 요구 → `Email not confirmed` | 개발 중엔 대시보드에서 'Confirm email' 잠시 끄기 (**배포 전엔 다시 켜기**) |
| 메일이 안 나간다 | 내장 메일은 테스트용 — 팀 멤버 주소로만, 시간당 두어 통 (`over_email_send_rate_limit`) | 커스텀 SMTP (Resend·SendGrid·SES·Postmark) |
| 확인 링크가 localhost로 | Site URL 설정 탓 | Authentication 의 Site URL·Redirect URLs 를 배포 주소로 |
| **RLS를 안 켜면** | 로그인한 **누구나 전체를 읽는다** | 표마다 행 수준 보안 켜기 |
| **키 두 개 혼동** | 비밀 키(secret/service_role)가 노출되면 **RLS를 우회해 DB 전체가 열린다** | 공개 키만 화면에(그래도 `.env`), 비밀 키는 코드·git·채팅 금지. 올렸다면 **즉시 폐기·재발급** |

#### 잠깐 멈춰 — 무엇을 손에 익혔나

여기서 짚어 준 말이 오늘의 요점이었다. **방금 익힌 건 '클래스 신청 앱' 자체가 아니라 다섯 단계의 절차다.** 어떤 서비스를 만들든 그대로 통한다. 다음 단원부터는 이 절차를 각자의 도메인으로 옮긴다 — 처음엔 틀(빈칸)을 주고, 점점 그 틀을 걷어 가며, 결국 혼자서 한 바퀴를 돌게 된다.

### 6. 내 도메인으로 날개 펴기

절차를 다 봤으니 이제 정해진 예시가 아니라 **만들고 싶은 것**을 만든다. 스택도, 순서도, 어디까지 갈지도 자유. 앞의 절차는 필요할 때 꺼내 보는 참고서다.

딱 하나만 붙잡으라고 했다 — **작게, 한 흐름이 끝까지 굴러가게.**

제출은 **완성이 아니라 '굴러가는 첫 조각'** 이면 된다. 오늘 만든 그대로 — 실행되는 저장소나 배포 주소(로컬만 됐으면 실행법 + 화면 캡처), 내 서비스 한 문장, 오늘 AI와 나눈 대화(**가장 효과적이었던 프롬프트 하나는 표시**), 회고 한 줄(무엇을 잘랐나 / 어디서 막혀 어떻게 풀었나 / 다음 한 걸음).

### 7. 막혔을 때 — 네 가지 규율

바이브 코딩은 **의도 → 생성 → 검토 → 반복 → 출시**의 반복이고, 초보와 능숙한 사람의 차이는 루프 자체가 아니라 **각 단계를 얼마나 단단히 조이느냐**다.

**① 한 번에 하나만.** 프롬프트 하나에 다섯 가지를 요구하면 몇 개는 맞고 몇 개는 틀린다 — 그럼 디버깅이 더 어려워진다. 고칠 때도 **"필요한 것만 바꿔줘"**.

**② 작동하면 저장.** 바뀔 때마다가 아니라 **'작동할 때마다'** 커밋한다.

**③ 막히면 되돌리고 리셋.** 같은 버그를 못 고치고 빙빙 돌면 랜덤하게 이것저것 바꾸라고 시키지 않는다 — **그게 코드를 이해 불가능하게 만드는 지름길**이다. 대신 5~10번마다 *"지금까지 뭐가 됐고, 뭐가 남았고, 지금 문제는 뭐다"* 로 요약해 AI의 초점을 다시 맞춘다.

**④ 이해 못 한 코드는 배포하지 않는다.** 시제품 단계에선 "다 수락"도 괜찮지만, 남에게 내보낼 거라면 그 코드가 무엇을 하는지 알아야 한다. Veracode 2025 GenAI 보고서에서 조사한 AI 생성 코드의 **45%가 보안 결함**이 발견됐다(그 연구의 스캔·분류 기준 결과이며 모든 AI 코드의 일반적 비율은 아니다).

#### 심화 — Git은 '저장 버튼'이 아니라 실험을 안전하게 만드는 기록 장치

이 섹션이 오늘 가장 밀도 높았다. 책상 비유로 세 장소를 나눈다.

| 장소 | 비유 | 의미 |
|---|---|---|
| working tree | 지금 손으로 펼쳐 놓은 원고 | 에디터에서 저장한 변경 |
| staging area (index) | 다음 기록 상자에 넣기로 **골라 둔** 원고 묶음 | `git add`는 자동 백업이 아니라 **선택** |
| repository | 확정된 사진첩 | `git commit` 으로 남긴 체크포인트 |

**되돌리기 명령은 이름이 비슷해도 위험이 다르다.**

- `git restore <파일>` — 작업 트리의 **커밋하지 않은** 변경을 버린다. 사라질 내용을 먼저 `git diff` 로 보는 습관이 필요하다.
- `git reset --hard <커밋>` — 브랜치·스테이징·작업 트리를 함께 맞춘다. **커밋하지 않은 작업을 실제로 지울 수 있는 강한 명령.** *"안 되면 하드 리셋"은 진단법이 아니다.*
- `git revert <커밋>` — **과거를 지우지 않는다.** 그 커밋의 효과를 반대로 적용하는 **새 커밋**을 만든다. 이미 푸시한 변경을 취소할 때 이력이 남아 안전하다.

> **reset은 내 로컬 실험의 책상 정리, revert는 공유된 역사에 남기는 취소 메모.**

**AI에게도 Git을 작업 규율로 요구한다** — *"수정 전에 `git status`와 관련 파일 diff를 요약해줘. 테스트가 통과하면 변경 목적 하나만 담아 커밋 후보를 제안해줘. **`reset --hard`나 강제 푸시는 내가 명시적으로 승인하기 전에는 실행하지 마**"*. 그리고 **비밀키가 diff에 보이면 커밋하지 않는다** — Git은 비밀을 자동으로 막아 주지 않는다.

좋은 체크포인트는 '오후 작업'처럼 **시간으로 쓰지 않는다.** "게시물 작성 뒤 새로고침해도 남는다", "잘못된 비밀번호에 오류가 보인다"처럼 **행동과 관찰 가능한 결과**로 쓴다.

> Git의 목적은 실수하지 않는 사람이 되는 것이 아니라, **실수해도 작은 비용으로 배우고 돌아오는 사람**이 되는 것이다.

#### 러버덕 디버깅 — 오리에게 설명하기

문제가 안 풀릴 때 고무 오리 인형에게 코드를 한 줄씩 **소리 내어** 설명하는 방법. 1999년 『실용주의 프로그래머』의 일화에서 왔다. 원리는 심리학의 **자기 설명 효과** — 머릿속으로 볼 때는 슬쩍 넘어가던 **당연하다고 여긴 전제**가, 말로 옮기는 순간 빈틈이 드러난다.

**바이브 코딩에서 내 '고무 오리'는 AI다.** 막혔을 때 "지금 뭘 하려는 거고, 무엇까지 됐고, 어디서 막혔는지"를 또박또박 적는 동안 문제의 상당 부분이 스스로 보인다.

#### 둠 루프 — 마지막 10%의 늪

"거의 다 됐는데" 버그 하나가 안 잡히고, AI는 "고쳤다"는데 실제론 안 고쳐지고, **프롬프트를 더 넣을수록 멀쩡하던 기능까지 깨지는** 상황. 운이 나빠서가 아니라 **구조적**이다 — 대화가 길어지며 맥락이 오염되고, AI에겐 "무엇이 무엇에 의존하는지"의 지도가 없어 **원인이 아니라 증상만 계속 땜질**한다.

빠져나오는 법 — ① 같은 프롬프트 반복 대신 **"한 발 물러서서 전체 그림을 다시 보자"** ② 마지막으로 작동하던 지점으로 되돌린 뒤 **새 대화로** 다시 시작 ③ "로그인 시스템 고쳐줘" 대신 **"로그인 폼이 데이터를 제대로 보내는지부터 확인하자"** 처럼 잘게 쪼개기.

주말 내내 붙잡던 버그를 포기하고 처음부터 다시 만들었더니 한 시간 만에 풀렸다는 사례도 있다. **막힘이 30분을 넘기면 더 파기 전에 멈추고 되돌리는 것이 대개 더 빠르다.**

#### 초보가 자주 밟는 지뢰

| 증상 | 처방 |
|---|---|
| 검증 없이 그대로 믿기 (AI 코드는 깔끔해 보여서 근거 없는 안심을 준다) | '완성품'이 아니라 **'초안'**으로 대하고 "이 코드가 뭘 하는지 설명해줘"로 검토 |
| 비밀키를 코드에 박아 커밋 (GitHub에 올리면 몇 분 만에 긁혀간다) | `.env` + 곧바로 `.gitignore`. 이미 노출했다면 **삭제가 아니라 재발급** |
| 예외·에러 처리 빼먹기 (AI는 "모든 게 정상인 경우"만 만든다) | **"빈 입력·네트워크 실패·잘못된 값도 처리해줘"** 라고 명시 |
| 불필요한 복잡도 (세 줄이면 될 일에 라이브러리 다섯 개 — 딸려 오는 취약점까지) | **"이거 없이 기본 기능만으로 안 돼?"** 되묻기 |

공통점은 하나 — **편함과 위험은 같이 온다.** AI를 '목발'이 아니라 **'가정교사'** 로 쓰는 것이 초보와 능숙한 사람을 가른다.

#### AI 말고 다른 길

- **에러 메시지를 '그대로 복사'해 검색** — 손으로 다시 치면 오타로 검색이 엉킨다. 결과가 없으면 파일명·변수명처럼 **내 프로젝트에만 있는 부분을 지워** 더 일반적으로 넓힌다. 긴 오류라면 **맨 마지막 줄**이 대개 가장 잘 맞는다.
- **커뮤니티에 '잘' 묻기** — ①목표 한 줄 ②재현되는 최소 코드 ③**정확한 에러 텍스트**(스크린샷 말고) ④이미 시도한 것.
- **최소 재현 예시(MRE)** — "남이 그대로 돌려도 같은 문제가 나는, 가능한 한 짧은 코드." 차가 이상할 때 차 전체가 아니라 **"브레이크 밟을 때 나는 소리"만** 떼어 보여주는 것과 같다. **좁히는 과정에서 답을 스스로 찾는 경우도 많다.**

순서를 기억한다 — **① 에러 그대로 AI에게 → ② 그대로 검색 → ③ MRE로 좁혀 커뮤니티에 질문.**

### 8. 오늘의 회고 질문

- 오늘 "자르기"가 가장 아까웠던 기능은? 그래도 자른 이유는?
- 막혔을 때 나를 가장 도와준 규율은? (한 번에 하나 / 작동하면 저장 / 막히면 리셋 / 이해한 것만 배포)
- 완성까지, 지금 가장 겁나는 부분은 무엇인가?

## 느낀 점 / 적용할 점

- **"자동차 타이어는 MVP가 아니다"가 오늘 가장 크게 남았다.** 그런데 내가 실제로 만든 것들을 돌아보니 우연히 잘 지켜 왔다 — 게임 세 개(레이싱·플랫포머·지뢰찾기)는 전부 **`index.html` 하나에서 한 흐름이 끝까지 굴러가는** 것부터 만들었다. 반대로 `ksk_coin` 은 F0~F9를 하루에 다 넣었는데, 그건 이미 F0(채굴 한 바퀴)이 굴러간 뒤에 얹은 것이라 스코프 크립이 아니라 **다음 탈것**이었다고 볼 수 있겠다. 구분선은 **"첫 흐름이 이미 끝까지 도는가"** 다.
- **`.gitignore` 를 먼저 걸고 시작하는 습관이 여기서 값을 했다.** 강의가 "비밀키를 코드에 박아 커밋 → 삭제가 아니라 재발급"을 지뢰로 꼽았는데, `saju_tarot` 의 `.env`·`field_key.txt`, 강의 원본(제3자 저작물)을 이미 그렇게 막아 두고 있다. 어제 `.omc/` 가 실수로 커밋된 걸 발견해 전역 제외 목록으로 옮긴 것도 같은 갈래다.
- **`git revert` 와 `git reset --hard` 의 구분은 이번에 처음 제대로 이해했다.** "reset은 내 책상 정리, revert는 공유된 역사에 남기는 취소 메모"라는 비유가 결정적이었다. 어제 `0905`(토요일) 강의노트를 되돌릴 때는 아직 푸시 전이라 reset 계열로 정리했는데, **이미 푸시한 블로그 글이었다면 revert 가 맞았다.** 공개 저장소에 올라간 뒤에는 이력을 바꾸지 않는다 — 규칙으로 적어 둘 만하다.
- **"AI 설명만 믿지 말고 로그를 눈으로 확인하라"** 는 것도 실감이 있다. 오늘 `ksk_coin` 의 임대수익률을 고칠 때도 백서 표에 적은 숫자와 실제 계산 결과가 맞는지 브라우저에서 직접 뽑아 대조했다. **"고쳤습니다"는 증거가 아니다.**
- **둠 루프 탈출법 중 "새 대화로 다시 시작"은 아직 안 해 본 카드다.** 나는 막히면 계속 같은 대화에서 밀어붙이는 편인데, 맥락 오염이 구조적 원인이라면 되돌린 뒤 새로 시작하는 게 더 빠를 수 있다. 다음에 30분 넘게 막히면 이걸 먼저 써 보겠다.
- **적용할 것 하나:** 다음 프로젝트에서는 PRD에 **"지금은 안 함(Won't) 5개"** 칸을 반드시 넣겠다. 지금까지 쓴 PRD들은 만들 것만 적었고 **안 만들 것을 명시한 적이 없다.** 그게 스코프 크립을 막는 장치라면 빈칸으로 둘 이유가 없다.
- **아직 안 정한 것:** 메인 퀘스트 01에 어떤 도메인을 낼지. `saju_tarot` 이 가장 크고 완성도도 높지만 과제 기한 이후 유료 전환을 계획하고 있어 성격이 다르다. "내 전문 분야의 이 불편을"로 시작하는 한 문장을 먼저 써 보고 정해야 한다.
