# 에이전트 = 모델 + 하네스 — MCP·스킬·규칙으로 '내 전용 조수' 만들기

## 핵심 요약
- 지금까지 써 온 도구가 사실 **에이전트**였다. 어시스턴트는 다음 줄을 추천하고 질문에 답하는 **조수**이고, 에이전트는 목표만 받으면 단계를 스스로 쪼개고 파일·터미널·검색까지 써서 일을 끝내는 **일꾼**이다. 둘은 칼로 자르듯 나뉘지 않고 정도의 차이다. 결정적 차이는 **반복(루프)** — 계획·실행·관찰·반성을 목표가 될 때까지 되풀이한다. 이 발상의 연구 이름이 **ReAct**(Yao et al., 2022)이고, 품질관리의 PDCA·공군의 OODA 루프와 같은 모양이다.
- 오늘의 열쇠 공식은 **에이전트 = 모델 + 하네스**다. 모델은 지능(Claude·GPT), 하네스는 그 지능을 감싸 실제로 일하게 만드는 실행 환경(루프·파일 접근·안전장치)이다. **같은 모델도 하네스에 따라 결과가 크게 달라진다.** 그래서 하네스를 강하게 만드는 세 가지 — MCP·스킬·규칙 — 이 오늘의 본론이다.
- **MCP는 'AI를 위한 USB-C'**다. AI는 기본적으로 내 DB·파일·캘린더를 모르는데, AI 3개 × 도구 5개면 연결을 15개 만들어야 하는 **M×N 지옥**이 된다. 공통 규격을 쓰면 **M+N**으로 줄어든다. Anthropic이 2024년 11월 공개했고 OpenAI(2025-03)·구글(2025-04)이 잇따라 채택, 2025년 말 리눅스 재단 산하 중립 재단으로 넘어가 **업계 공용 약속**이 됐다. 서버가 건네는 것은 **도구(실행)·자원(읽기)·프롬프트(템플릿)** 세 가지다.
- **스킬은 반복 작업을 외워 두는 플레이북**이다. 기술적으로는 폴더 하나 + `SKILL.md` 이고, 머리말(name·description)과 본문으로 나뉜다. 영리한 점은 **점진 공개** — 평소엔 이름과 한 줄 설명만(30~50토큰) 물고 있다가 필요할 때만 본문을 펼친다. 그래서 수십 개를 켜 둬도 느려지지 않고, **description 을 잘 쓰는 것이 가장 중요**하다(AI가 그 한 줄로 꺼낼지 판단하므로). 헷갈리지 않는 세 갈래: **새 능력·연결 = MCP / 항상 이렇게 = 규칙(CLAUDE.md·AGENTS.md) / 반복하는 다단계 작업 = 스킬.**
- **도구 이름을 외우는 건 의미가 적다.** 하네스는 브라우저형·편집기형·터미널형·클라우드형 네 부류뿐이고, 나누는 기준은 "어디서 돌고 내가 얼마나 지켜보느냐" 하나다. 고를 때 볼 것은 모델 선택권·비용 구조·오픈소스 여부·터미널 편의·맡길지 지켜볼지 다섯 가지이며 **정답이 아니라 내 조건**이다. 그리고 편해질수록 위험도 같이 온다 — 사람들은 권한 요청의 **약 93%를 그냥 승인**하고, 에이전트는 보통 채팅의 **4배**(멀티 에이전트는 15배) 토큰을 쓴다.

## 상세 내용

### 1. 어시스턴트에서 에이전트로 — 도구의 정체

에이전트를 한 문장으로 줄이면 "목표를 주면 필요한 도구를 골라 쓰고 결과를 보며 다음 수를 정하기를 끝까지 반복하는 AI"다. 사람이 하는 건 "이렇게 저렇게 클릭해"가 아니라 "로그인 기능을 붙여 줘"처럼 **목표를 주는 것뿐**이고, 세부 단계는 AI가 짠다. 코딩에만 해당하는 얘기가 아니라 고객 문의를 처리하든 보고서를 쓰든 뼈대는 같다.

| 구분 | 어시스턴트 | 에이전트 |
|---|---|---|
| 하는 일 | 다음 줄 추천, 질문에 답 | 여러 파일 수정·명령 실행·반복 |
| 단계를 정하는 주체 | 사람 | AI가 스스로 |
| 도구 사용 | 거의 없음 (텍스트 위주) | 파일·터미널·검색 등 |
| 비유 | 곁에서 거드는 조수 | 일을 맡아 끝내는 일꾼 |

**'에이전트'는 AI가 지어낸 신조어가 아니다.** 부동산 에이전트·여행사 에이전트처럼 원래 "나 대신 뛰어서 일을 처리해 주는 사람"이고, 어원은 라틴어 *agere*(행하다)다. AI 교과서의 고전인 러셀·노빅(1995)은 인공지능이라는 학문 자체를 "주변을 살펴보고 목표를 위해 스스로 행동하는 존재, 즉 에이전트를 연구하는 일"로 정의했다. 1990년대에도 메일을 읽고 일정을 잡아 주는 프로그램을 에이전트라 불렀다. 달라진 건 그 '머리' 역할을 이제 LLM이 맡는다는 것뿐이다.

AI가 여기까지 온 경로는 네 단계였다. **2020~2021년** 한 번 묻고 한 번 답하는 단일 턴(편집기에서는 자동완성이 전부) → **2022년 말 ChatGPT** 로 앞 대화를 기억하는 멀티턴 → **2023년** 모델이 정해진 방식으로 바깥 도구를 부르며 말 대신 **행동**을 시작 → **2024년 이후** 여기에 **반복**이 얹혀 에이전트가 됐다. 겉모습은 도구마다 달라도 속은 닮아 가는데, 그래서 AGENTS.md·스킬·MCP처럼 "한 번 적어 두고 계속 쓰는 맥락"이 어느 도구에서나 공통으로 등장한다.

**루프의 네 단계**는 계획(Plan) → 실행(Act) → 관찰(Observe) → 반성(Reflect)이고, 목표를 이룰 때까지 반복한다. 이 '생각하고-행동하고-관찰한다'를 연구자들은 **ReAct**(Reasoning + Acting)라 부른다. Shunyu Yao 등이 2022년 10월 arXiv에 공개하고 2023년 ICLR에서 발표했으며, 저자 소속에 Princeton과 Google Research가 포함된다.

왜 한 번에 정답을 내는 것보다 나은가. **Thought는 파일의 실제 내용이나 명령의 오류를 모른 채 세운 추측**일 수 있다. Action은 바깥 세계에 질문을 던지는 단계이고 Observation은 그 질문이 돌려준 **사실**이다. 다음 Thought는 그 사실을 재료로 다시 쓰인다. 예를 들어 "로그인이 안 된다"면 곧바로 코드를 고치지 않고 먼저 오류 로그를 읽어(Action) 401인지 환경변수 누락인지 관찰한(Observation) 뒤에야 수정 방법을 고른다(Thought). 이 교차가 환각을 없애지는 않지만 **추측을 검증 가능한 증거로 교체**한다.

그래서 좋은 지시는 "고쳐 줘"에서 끝나지 않고 "먼저 관련 파일과 오류를 확인하고, 수정 뒤에는 테스트를 실행해 결과를 보고해 줘"처럼 **관찰 지점을 요구**한다.

**2023년 봄의 소동 — AutoGPT.** GPT-4 직후 "목표 한 줄만 주면 알아서 끝까지"라는 BabyAGI·AutoGPT가 화제가 됐고, AutoGPT 저장소는 몇 주 만에 GitHub 별 10만 개를 넘겼다. 그런데 돌려 보니 **언제 멈출지 몰라 무한 반복하고, 엉뚱한 방향으로도 계속 호출해 요금이 커지고, 중간 확인이 없으면 틀린 목표로 달렸다.** 그래서 오늘의 에이전트는 "완전 자율"보다 **작은 작업 단위·명확한 권한·중간 확인**을 더 중요하게 본다.

### 2. MCP — AI를 내 데이터에 꽂는 USB-C

아무리 똑똑한 AI도 기본적으로는 학습한 것만 안다. 내 DB, 내 파일, 우리 회사 문서는 모른다. 복사해 붙여넣을 수도 있지만 도구가 늘면 **AI 3개 × 도구 5개 = 연결 15개**를 일일이 만드는 지옥(M×N 문제)이 된다.

**MCP(Model Context Protocol)** 는 이 문제를 푸는 표준 규격이다. 예전엔 기기마다 충전기가 달랐지만 USB-C로 통일되니 아무 기기나 꽂히는 것처럼, 도구를 한 번 MCP 규격으로 만들면 MCP를 지원하는 아무 AI에나 꽂힌다. 앱 M개는 client를 한 번, 서비스 N개는 server를 한 번 구현하면 되므로 연결이 **M×N → M+N** 으로 줄어든다.

정말 흥미로운 건 **경쟁사들이 같은 규격에 손을 얹었다**는 점이다. Anthropic이 2024년 11월 공개 → OpenAI 2025년 3월 채택 → 구글 2025년 4월 채택 → 2025년 말 리눅스 재단 산하 Agentic AI Foundation으로 이관. 그래서 MCP는 특정 회사 기능이 아니라 **업계 공용 약속**이고, 한 번 익히면 도구가 바뀌어도 계속 쓸 수 있다.

구조는 세 조각이다. **host** 는 AI를 담은 앱(코딩 도구), 그 안의 **client** 가 연결을 관리하고, **server** 는 Notion·파일시스템·DB 같은 바깥 기능을 MCP 방식으로 내놓는다. server가 건네는 것은 세 종류다.

| 이름 | 뜻 | 예 |
|---|---|---|
| 도구(Tools) | AI가 **실행**하는 기능 | 검색하기, DB 조회하기 |
| 자원(Resources) | AI가 **읽어 들이는** 데이터 | 파일, 문서, 기록 |
| 프롬프트(Prompts) | 미리 만들어 둔 **요청 템플릿** | |

실제로 많이 붙이는 것은 파일시스템(내 폴더 읽고 쓰기), GitHub(이슈·코드·커밋), 브라우저 자동화(Playwright로 실제 브라우저를 열어 클릭·캡처), Slack, Notion, 데이터베이스, 구글 드라이브·캘린더다. 이제 **공식 레지스트리**(registry.modelcontextprotocol.io)에서 앱스토어처럼 찾는다.

**주의가 둘 있다.** 첫째, 공개 MCP 서버가 수천 개로 급증했고 검증 안 된 것도 많다 — 모르는 서버를 섣불리 붙이지 말고 회사가 직접 낸 공식 서버부터 쓴다. AI에게 내 데이터·계정 접근 권한을 주는 일이다. 둘째, **플러그 모양이 같다고 모든 기기가 같은 권한을 갖는 것은 아니다.** MCP는 연결 규칙이지 자동 안전 보장이 아니다. 특히 tool은 실제 행동을 하므로 **"읽기" 도구부터 연결하고, 쓰기·삭제·배포처럼 되돌리기 어려운 권한은 승인 과정을 둔다.**

흥미로운 현실은 공개적으로 널리 쓰이는 MCP 서버는 아직 손에 꼽지만 **회사 내부용 MCP(사내 DB·문서 연결)가 가장 값지다**는 평가다. 남에게 공개하지 않아도 내 데이터에 AI를 붙이는 것만으로 큰 힘이 된다.

### 3. 스킬 — 반복 작업을 AI에게 외워 두기

"우리 브랜드 톤으로 정리해 줘"를 매번 처음부터 설명하고 있다면 지겹고 결과도 그때그때 달라진다. 이것을 **재프롬프트(re-prompting) 문제**라 한다.

**스킬은 자주 하는 작업을 한 번 적어 두고 계속 꺼내 쓰는 설명서**다. 기술적으로는 그냥 폴더 하나이고, 그 안 `SKILL.md` 에 "무엇을, 언제 쓰는지"를 적어 두면 AI가 관련된 일을 만났을 때 알아서 꺼내 쓴다. 파일은 두 부분 — 맨 위 **머리말**(name·description)과 그 아래 **본문**(실제 지시).

핵심 원리는 **점진 공개(progressive disclosure)** 다. AI는 평소 머리말의 name과 description만(30~50토큰 수준) 훑고 있다가, 지금 하는 일이 그 설명과 맞을 때만 본문 전체를 읽어 온다. 그래서 **수십 개를 켜 둬도 평소엔 거의 공짜**이고 필요한 순간에만 펼쳐진다. **description을 잘 쓰는 게 중요한 이유가 여기 있다** — AI가 언제 이 스킬을 꺼낼지를 그 한 줄로 판단한다.

남이 만든 걸 가져다 쓰는 게 빠를 때도 많다. 가장 유명한 건 Anthropic의 **문서 스킬 네 개**(pptx·xlsx·docx·pdf)로, "이 자료로 발표 슬라이드 만들어 줘"라고 하면 뒤에서 조용히 돌아가 마크다운 흉내가 아닌 **서식까지 갖춘 진짜 파일**을 뽑아 준다. Claude의 문서 생성 기능이 통째로 이 스킬들 위에서 돌아가고 소스도 공개돼 있어 교본으로 자주 인용된다. 그 밖에 '스킬 만드는 스킬', 'MCP 빌더' 같은 것도 있다.

**조심할 것** — 스킬은 결국 'AI에게 주는 지시문 + 실행 코드'라 출처가 불분명한 걸 켜면 위험하다. 내가 만들었거나 공식 저장소에서 온 것 위주로 쓰고, 남의 스킬은 안에 뭐가 들었는지 한 번 열어 보고 쓴다.

스킬과 비슷하지만 더 기본이 되는 게 **규칙 파일**이다. "우리 프로젝트는 이런 규칙이야"를 파일 하나에 적어 두는 것으로, `AGENTS.md` 또는 `CLAUDE.md` 라 부르고 공식 설명은 이걸 **"에이전트를 위한 README"** 라고 한다. 많은 도구가 대화를 시작할 때 자동으로 먼저 읽는다(**단, Claude Code는 CLAUDE.md만 자동으로 읽는다**). 적으면 유용한 것은 프로젝트 개요, 자주 쓰는 명령(설명보다 명령어를 먼저), 규칙·컨벤션, **하지 말 것**이다. 예전엔 도구마다 파일 이름이 제각각이었는데 2025년 여러 회사가 모여 AGENTS.md 공통 표준을 만들었다.

| 내가 원하는 것 | 무엇을 쓰나 |
|---|---|
| AI에게 **새 능력·연결**을 주고 싶다 (내 DB·도구에 붙이기) | **MCP** |
| AI가 **항상** 이런 식으로 행동하게 하고 싶다 | **규칙** (CLAUDE.md / AGENTS.md) |
| **반복하는 다단계 작업**을 자동화하고 싶다 | **스킬** |

한 문장으로: **스킬은 선반에서 꺼내 쓰는 '방법서', 규칙은 프로젝트의 '상시 안내문', MCP는 도구를 꽂는 '어댑터'.** 서로 경쟁이 아니라 함께 쓴다.

### 4. 하네스 종류 — 어떤 AI 코딩 도구를 고를까

하네스는 종류가 많지만 크게 **네 부류**뿐이고, 나누는 기준은 **"어디서 돌고, 내가 얼마나 지켜보느냐"** 하나다.

| 형태 | 특징 | 예 |
|---|---|---|
| **브라우저형** | 클릭으로 만들고 배포까지. 문턱이 가장 낮음 | Lovable · Bolt · Replit |
| **편집기형** | 고친 걸 눈으로 보며 승인·취소 | Cursor · Copilot · Cline |
| **터미널형** | 깊고 강력하지만 낯섦 | Claude Code · Codex CLI · agy · Aider |
| **클라우드/비동기형** | 통째로 맡기면 백그라운드에서, 결과는 **초안** | Devin · Google Jules |

앞의 셋은 내 컴퓨터에서 내가 지켜보는 쪽, 마지막은 멀리 맡기고 결과만 받는 쪽이다.

커뮤니티에서 가장 자주 나오는 결론은 **"정답 하나는 없다"** — 프레임워크 고를 때와 같이 정답이 아니라 내 조건이다. 볼 것은 다섯 가지: ① **모델을 골라 쓸 수 있나**(오픈소스 계열이 자유롭다) ② **비용 구조**(월 정액인가, 프로그램은 무료지만 쓴 만큼 API 요금인가 — 후자는 확 오른다) ③ **오픈소스 여부**(접어도 남이 이어받아 살릴 수 있다. 실제로 2026년 한 오픈소스 확장의 종료가 이 리스크를 보여줬다) ④ **터미널이 편한가** ⑤ **맡길까 지켜볼까**. 그리고 **실무자도 하나만 쓰지 않는다** — 어려운 건 터미널, 일상 편집은 편집기, 가끔 클라우드를 섞어 쓴다.

초보 순서는 브라우저형(문턱 최저) → **편집기형**(고친 걸 보며 승인·취소하니 배우기 좋다. 무료로 가볍게는 Copilot 무료 티어, 본격적으로는 Cursor) → 터미널형(검은 화면이 익숙해진 뒤)이며, **클라우드형은 초보의 첫 도구로 권하지 않는다** — 결과를 검토·판단할 안목이 없으면 통제감이 떨어진다.

**안전과 권한.** 에이전트는 단순 답변기가 아니라 실제로 파일을 지우고 명령을 실행하고 외부에 요청을 보낼 수 있다. 그래서 좋은 도구는 위험한 행동 전에 묻는데, 문제는 반복되면 사람이 무심코 "예"만 누른다는 것이다 — **사용자들이 권한 요청의 약 93%를 그냥 승인**한다는 조사가 있다. 권한 방식은 이름이 달라도 개념은 같다(매번 확인 / 편집만 자동 / 위험한 것만 막고 나머지 자동 / 아무것도 안 물어봄). 마지막은 **폐기해도 되는 실험 환경에서만** 쓰라고 공식 경고가 붙는다.

지킬 습관 세 가지: 중요한 폴더에서 자동 수락을 켜지 않기, 위험한 작업 전 **되돌릴 지점(커밋)** 만들기, 그리고 핵심 한 문장 — **"아무것도 안 물어봄"과 "중요한 것에 대한 전체 접근"을 동시에 켜지 마라.**

**비용.** 에이전트는 루프를 여러 번 돌고 매번 앞선 대화와 도구 결과를 통째로 다시 포함하므로 보통 채팅보다 토큰을 **약 4배**, 여러 에이전트가 협업하면 **약 15배까지** 쓴다. 단계 수가 늘면 총 입력량은 선형보다 빠르게(대략 n²에 가깝게) 커지고 대기 시간도 늘어난다. 그래서 실전 규율은 **한 번에 거대한 작업을 시키지 말고 작게 쪼개기**, 큰 파일·긴 로그는 필요한 부분만 주기, 끝나면 짧은 요약만 남기기다. "토큰을 무조건 적게"가 아니라 **다음 판단에 필요한 증거만 남기는 것**이 목표다.

**컨텍스트 부패(context rot).** 대화가 길어져 컨텍스트 창이 차면 아까 정한 걸 잊고, 앞뒤가 안 맞고, 없는 파일명을 지어낸다. 창이 커져도 입력이 길수록 성능이 떨어지는 경향은 여전하다. 해법은 개념상 둘 — **요약해 압축하기**(한 작업이 끝난 시점)와 **완전히 새 대화로 리셋하기**(전혀 다른 작업으로 넘어갈 때). 규칙 파일에 적은 내용은 리셋해도 유지된다. **한 가지 일이 끝나면 새 대화로 시작하는 게 오히려 결과가 좋다.**

이 밖에 **서브에이전트**(지휘하는 AI가 하위 AI에게 조사를 맡기고 요약만 받는 방식 — 강력하지만 토큰이 크게 늘어 실무에선 "지휘는 똑똑한 모델, 잔일은 값싼 모델"로 등급을 나눈다), **로컬 모델**(Ollama 같은 도구로 오픈 모델을 내 컴퓨터에서 — 입력이 기기 밖으로 안 나가고 사용료·오프라인 이점이 있지만 성능과 사양에서 밀린다. "민감한 자료는 로컬, 어려운 작업은 클라우드"), **열린 모델과 닫힌 모델**(Anthropic은 가중치를 공개하지 않고, OpenAI는 최상위는 닫되 gpt-oss는 풀었다. 정작 가장 센 오픈웨이트는 중국에서 나오는데 Kimi K3·DeepSeek·Qwen·GLM이 자유 라이선스로 프런티어에 바짝 붙었다. 다만 SWE-bench Verified 최상단은 아직 폐쇄 모델이 지키고 있고 '오픈웨이트 = 공짜'도 아니다)를 다뤘다.

**Devin 논쟁**도 짚었다. 2024년 3월 Cognition이 "세계 최초의 AI 소프트웨어 엔지니어"로 공개하고 프리랜서 플랫폼에서 돈을 번다는 시연이 화제가 됐지만, 곧 홍보만큼 과제를 끝내지 못하고 잘 되는 장면만 골라 담았다는 반론이 나왔다. 교훈 둘 — **화려한 데모는 가려서 볼 것**("된다"는 시연과 "믿고 맡길 수 있다"는 전혀 다르다), 그럼에도 이 소동이 자율 코딩 에이전트 경쟁의 촉매였다는 것.

결론은 **도구 이름을 외우는 건 의미가 적다**는 것이다. 이름·가격·무료 정책·회사가 짧은 기간에도 바뀌므로 특정 도구의 인수·중단은 외울 사실이 아니라 **선택 직전에 공식 공지로 확인할 정보**다. 대신 오늘 배운 개념(에이전트 = 모델 + 하네스, MCP, 스킬)을 잡아 두면 새 도구가 나와도 "하네스가 이렇구나, MCP 되나?"로 판단할 수 있다.

### 5. 스킬 너머 — 확장과 요즘 흐름

여기부터는 당장 필요하지 않고, 스킬·MCP에 익숙해지면 만나게 되는 이야기다.

**Claude 플러그인** — 스킬 하나, MCP 연결 하나를 낱개로 쌓으면 남에게 "내 세팅 그대로 써 봐" 하고 넘기기 번거롭다. 플러그인은 스킬·서브에이전트·슬래시 명령·자동화 훅·MCP 연결을 **한 꾸러미로 묶어 명령 한 줄로 설치**한다. 공식 모음(claude-plugins-official)과 커뮤니티 모음(claude-plugins-community)이 있고, 많이 켤수록 AI가 읽어야 할 맥락이 늘어 느려지니 지금 쓸 것만 켠다. 진짜 빛나는 건 팀에서다 — 잘하는 한 사람 머릿속에만 있던 노하우가 설치 한 번으로 모두의 것이 되고, 버전이 붙어 되돌리기도 된다.

**에이전트 팀을 통째로 얹기** — 여러 전문 에이전트와 스킬을 한꺼번에 얹어 Claude Code를 '지휘자'로 만드는 오픈소스 레이어가 있다. **oh-my-claudecode**는 플러그인으로 얹는 '팀 우선' 오케스트레이션 레이어이고, **oh-my-openagent(omo)** 는 한발 더 나아가 모델을 가리지 않아 "잔일엔 값싼 모델, 판단엔 똑똑한 모델"로 골라 쓴다. 첫날부터 손댈 도구는 아니지만, "AI 하나에게 다 시키기"에서 "여러 전문 AI를 지휘하기"로 넘어가는 흐름의 끝에 이런 레이어가 있다는 것은 알아 둘 값어치가 있다.

**명세 주도 개발(spec-driven development)** — 스킬과 AGENTS.md의 공통점은 시키기 전에 '무엇을, 어떻게'를 먼저 글로 적어 둔다는 것이다. 이를 프로젝트 전체로 키운 방식이다. 아무 설명 없이 "만들어 줘"만 던지면 빠르지만 AI가 의도에서 벗어나거나 없는 기능을 지어내기 십상이라, 코드 전에 요구사항·설계·할 일을 문서로 정한다. **과제로 써 본 PRD가 바로 그 명세의 출발점이었다.** 도구로는 GitHub의 **Spec Kit**(별 12만 개 이상), 아마존의 **Kiro**, 더 가벼운 **OpenSpec** 이 있다. 다만 만능은 아니어서 요즘 결론은 **섞어 쓰기** — 탐색·시제품은 대화로, 오래 유지할 것은 명세로. 진짜 값어치는 도구가 아니라 **"만들기 전에 한 번 더 생각하게 만든다"** 는 데 있다.

**컴파운드 엔지니어링** — 일할 때마다 그 경험을 규칙·스킬로 남겨 **다음 일이 이전 일 위에 쌓이게** 하는 방법론이다. 버그를 한 번 고치면 그 교훈을 규칙 파일에 적어 AI가 다음부터 자동으로 지키게 한다. Nous Research의 **Hermes** 가 이를 도구로 구현했는데, 보통 AI는 대화창을 닫으면 잊지만 Hermes는 기억을 남기고 스스로 스킬을 만들어 **오래 쓸수록 똑똑해지도록** 설계됐다. 만든 쪽 말이 인상적이다 — "진짜 열쇠는 더 똑똑한 모델이 아니라 모델을 감싸는 더 똑똑한 껍데기(하네스)."

**루프 엔지니어링과 'Ralph'** — 루프를 사람이 직접 설계하는 흐름이다. 개발자 제프리 헌틀리가 퍼뜨린 Ralph는 방법이 놀랄 만큼 단순하다. **같은 지시(명세)를 계속 다시 주고, 한 번에 한 가지만 하고 커밋하기를 목표를 이룰 때까지 반복**한다. 진행 상황은 대화 기억이 아니라 **파일과 git에 쌓아** 둔다. 왜 하나의 긴 대화 대신 이렇게 하나 — **컨텍스트 부패** 때문이다. 2023년 AutoGPT가 '무한 반복'으로 실패했던 자리를 **'멈출 기준(명세) + 파일에 쌓는 진행'** 으로 다시 푼 셈이다. 헌틀리는 이 방식으로 프로그래밍 언어 하나를 약 300달러어치 호출로 만들어 화제가 됐다. Claude Code에는 목표만 주면 도는 `/goal` 명령이 생겼고, Claude Code를 만든 보리스 체르니는 "나는 이제 프롬프트하지 않는다, 루프를 돌리고 그 루프가 대신 프롬프트한다"고까지 말한다. 다만 안전장치가 없으면 무한 반복·요금 폭발이 흔하니 **멈출 기준과 검토는 여전히 사람 몫**이다.

**MCP에서 '스킬 + CLI'로** — MCP는 편하지만 공짜가 아니다. 연결해 두면 AI가 도구 설명서를 미리 통째로 읽어 컨텍스트를 꽤 잡아먹는다. 그래서 2026년 들어 **AI가 원래 알고 있는 명령줄 도구(CLI)를 그냥 쓰게 하자**는 반작용이 생겼다. 깃허브 작업은 `gh` CLI가 이미 있고 AI가 학습으로 알고 있으니, MCP 서버를 세우는 대신 "gh로 이슈 목록 가져와"라고 시키면 된다. 한 벤치마크에서 같은 일에 **CLI 약 1천 토큰 vs MCP 약 4만 토큰**, **800토큰짜리 스킬 파일이 2만 8천 토큰짜리 MCP 설명서보다 나았다**는 결과도 있다. 다만 이 '무겁다'는 문제도 도구 쪽에서 손보고 있어, 요즘 Claude Code는 MCP 도구를 처음부터 다 읽지 않고 필요할 때 검색해 불러오는 **툴 서치**를 기본으로 쓴다. 결론은 "셋 중 하나가 아니라 **스킬·MCP·CLI를 함께**" — 혼자 작은 걸 만들 땐 '이미 있는 CLI + 짧은 스킬'이 가볍고, 여럿이 쓰고 권한을 챙겨야 하면 MCP다.

## 느낀 점 / 적용할 점
- 오늘 배운 것을 **이틀에 걸쳐 거의 그대로 실습한 셈**이 됐다. 강의가 "반복하는 다단계 작업은 스킬"이라고 한 그대로 `html-game-deploy`(게임 3개를 만들며 세 번 반복한 절차), `blog-post`(포스트 8개가 같은 규격), `lecture-extract`(추출 스크립트를 네 번 다시 짠 것)를 스킬로 뽑았고, "항상 이렇게 행동하라"는 것은 `CLAUDE.md` 로 분리했다. **세 갈래(MCP / 규칙 / 스킬)를 머리로 아는 것과 내 폴더에 실제로 나누어 놓는 것은 다른 일이었다.**
- 특히 **description 한 줄이 스킬의 성패를 가른다**는 말이 실감났다. 점진 공개 때문에 AI는 평소 그 한 줄만 보고 꺼낼지 판단하므로, `blog-post` 의 description에 "블로그에 올려줘", "글 날짜가 하루 밀렸어" 같은 **실제로 내가 할 말**을 넣어 둔 것이 잘한 선택이었다. 반대로 이름을 `blog_post`(밑줄)로 착각했을 때 아무것도 안 불려 나온 것도 이 구조 때문이었다.
- **"에이전트 = 모델 + 하네스"의 하네스가 내 손에 있다**는 게 오늘의 가장 큰 수확이다. 어제 `oh-my-claudecode` 를 알아본 것이 강의 5번에 그대로 나와서 놀랐다 — 낱개로 쌓은 스킬·MCP를 꾸러미로 묶는다는 플러그인 설명이, 내가 설치해 놓고 정체를 몰랐던 그것이었다.
- **컴파운드 엔지니어링**이 지금 내가 하고 있는 일에 이름을 붙여 줬다. 강의 원본 추출을 네 번 다시 짠 것은 **경험을 남기지 않았기 때문**이었고, 이번에 스크립트를 `.claude/skills/` 에 고정하면서 그 반복이 끝났다. "다음 일이 이전 일 위에 쌓이게" — 앞으로 무언가를 두 번째로 하고 있다고 느끼면 그때 스킬로 남겨야 한다.
- **권한 요청 93%를 그냥 승인한다**는 숫자가 제일 무서웠다. 나도 승인 창을 거의 읽지 않고 눌러 왔다. 그리고 "아무것도 안 물어봄과 중요한 것 전체 접근을 동시에 켜지 마라"는 문장은 `C:\AI-Agent` 처럼 **저장소 14개가 섞여 있는 폴더**에서 특히 중요하다 — 루트에서 잘못 `git add` 하면 서브모듈 포인터가 깨진다는 걸 이미 확인했으니, 자율 실행 모드는 커밋을 정리한 뒤에만 쓰기로 했다.
- **컨텍스트 부패**와 "끝나면 새 대화로"는 당장 바꿀 습관이다. 그동안 한 대화에 게임·블로그·사주타로를 다 욱여넣었는데, 규칙 파일에 적은 내용은 리셋해도 유지된다는 걸 알았으니 이제 작업 단위로 끊는 편이 낫다. `CLAUDE.md` 를 만들어 둔 것이 그 준비였던 셈이다.
- **MCP → 스킬 + CLI 흐름**은 내 상황에 그대로 맞는다. 혼자 작은 걸 만드는 중이고 `gh` 가 이미 깔려 있으니, GitHub용 MCP를 붙이는 대신 스킬에 `gh` 명령을 적어 두는 쪽이 가볍다. 실제로 `html-game-deploy` 스킬에 `gh repo create` 와 `gh api …/pages` 를 적어 둔 것이 우연히 이 방향이었다.
