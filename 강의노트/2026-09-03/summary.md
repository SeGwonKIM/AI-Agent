# 백엔드가 필요한 이유부터 배포·보안, 풀스택 연결까지

## 핵심 요약
- 화면(프론트)만 있으면 "새로고침하면 사라짐 / 남에게 링크를 줘도 안 열림 / 컴퓨터를 끄면 서비스도 꺼짐"이라는 세 증상이 생기는데, 원인은 하나 — 24시간 켜져서 데이터를 저장하고 세상과 연결해 주는 **백엔드(서버)**가 없기 때문이다.
- 주소 하나가 화면이 되기까지는 도메인/DNS(이름→IP) → 서버·호스팅(내부망/외부망, NAT) → 포트·방화벽(어느 문으로) → HTTP/HTTPS(무슨 말로, 패킷으로 쪼개져 이동)의 네 조각이 순서대로 작동하며, 응답에 붙는 세 자리 상태 코드(2xx 성공·3xx 리다이렉트·4xx 내 잘못·5xx 서버 잘못)가 문제 위치를 알려 준다.
- 백엔드는 "요청을 받아 → 처리하고 → 응답한다"는 한 문장으로 요약되며, 엔드포인트(API)·CRUD(만들기/읽기/고치기/지우기)·JSON(공용 데이터 형식)이 그 뼈대를 이룬다. 진짜 가치는 "프론트는 못 믿는다"는 원칙 아래 가격·수량·권한 같은 검증을 서버에서 다시 하는 것이다.
- AI가 생성한 코드는 약 45%에 보안 결함이 있을 정도로 "돌아가지만 안전하지는 않은" 경우가 많아, 입력값 검증·비밀 값은 환경변수로 분리·비밀번호는 솔트+해시(bcrypt)로 저장·인증(로그인 확인)과 인가(권한 확인) 구분·쿠키/세션을 사람이 직접 프롬프트로 요구하고 점검해야 한다.
- 배포는 화면(Vercel·Netlify 등)·서버(Render·Railway 등)·데이터(Supabase 등)를 각각 잘하는 곳에 나눠 올리고 GitHub 연동으로 코드 변경 시 자동 배포되는 흐름이며, 무료 티어의 함정(잠듦·기한 만료·요금 폭탄)과 프론트-백엔드 연결 시 자주 겪는 문제(계약 불일치·CORS·환경변수 누락)를 알아 두면 대부분의 "왜 안 되지?"를 피할 수 있다. 과제는 튜토리얼로 백엔드를 한 바퀴 돌리거나(갈래 A), 자신의 서비스에 백엔드 한 겹을 붙여 배포하는 것(갈래 B)이다.

## 상세 내용

### 1. 화면 뒤에 서버가 필요한 이유
밤새 만든 화면을 친구에게 보여줘도 안 열리고(`localhost`는 "지금 이 컴퓨터"만 가리키는 주소라 친구 컴퓨터에선 아무것도 없다), 노트북을 닫았다 열면 입력한 내용이 사라진다. 세 증상(새로고침 시 데이터 소실·남이 못 엶·꺼지면 서비스도 꺼짐)의 공통 원인은 "내 컴퓨터 안에만 있고 세상과 연결된 뒤편이 없다"는 것이며, 그 뒤편이 백엔드다. 클라이언트(손님)와 서버(24시간 주방)에 비유하면, 프론트엔드는 손님 눈에 보이는 홀이고 백엔드는 데이터를 저장·확인·계산하는 눈에 안 보이는 주방이다. "여러 사람이 나눠 쓰거나, 껐다 켜도 남아야 하거나, 비밀이 오가는 것"은 서버가 필요하고, "화면 안에서 잠깐 보이고 마는 것"(색 변경, 애니메이션)은 서버 없이도 된다는 판단 기준도 제시된다. 인터넷의 역사(1969 ARPANET → TCP/IP → 1989~91 웹·HTTP 탄생 → 2000년대 클라우드)를 훑으며, 오늘날 비전공자도 클릭 몇 번으로 서버를 빌릴 수 있게 된 배경을 설명한다.

### 2. 네트워크 기본기 — 주소가 화면이 되기까지
`mysite.com` 입력부터 화면이 뜨기까지 네 조각을 순서대로 다룬다. ① **도메인·DNS** — 도메인은 사람이 외우는 이름이고 DNS가 이를 IP로 변환하며, 도메인이라는 '한 겹' 덕분에 서버를 옮겨도 주소는 그대로고, 하나의 이름으로 여러 서버(부하 분산·CDN)를 연결하거나 서브도메인으로 구조화할 수 있다. 자물쇠(HTTPS)는 '믿을 만한 회사'의 증명이 아니라 '통신이 암호화됐다'는 뜻일 뿐이라 피싱 사이트도 자물쇠를 달 수 있음을 주의한다. ② **서버·호스팅** — 24시간 켜진 컴퓨터를 클라우드(아마존·구글 등)에서 빌려 쓰는 방식이 표준이 되었고, 내부망(LAN, 사설 IP)과 외부망(WAN)을 공유기(NAT)가 가로막아 평소엔 안전하지만 그래서 `localhost`가 밖에서 안 보인다. ③ **포트·방화벽** — IP가 건물 주소라면 포트는 호실 번호(웹은 보통 80/443)이고, 방화벽이 불필요한 문을 막는다. ④ **HTTP/HTTPS** — 요청/응답으로 오가는 공통 언어이며, HTTPS는 공개키·개인키 방식(TLS 핸드셰이크)으로 중간에서 못 훔쳐보게 암호화한다. 데이터는 패킷으로 쪼개져 각자 다른 경로로 이동한 뒤 도착지에서 재조립되는데(TCP/IP), 이 덕분에 인터넷 일부가 고장 나도 전체가 멈추지 않는다. 마지막으로 상태 코드(200 성공, 301/302 이동, 401 인증 필요, 403 권한 없음, 404 없음, 429 과다 요청, 500 서버 오류)를 신호등에 비유해 정리하고, 브라우저 개발자도구의 네트워크 탭에서 직접 확인해 보는 실습으로 마무리한다.

### 3. 백엔드가 실제로 하는 일 — 요청을 받아 처리하고 돌려주기
백엔드의 동작은 "요청을 받아서, 처리하고, 응답을 돌려준다"는 한 문장으로 요약된다. 백엔드는 통째로 열려 있지 않고 정해진 창구(엔드포인트, 예: `GET /products`, `POST /login`)만 공개하며 이 창구들의 묶음이 API다. 대부분의 서비스는 데이터에 대해 CRUD(Create·Read·Update·Delete) 네 가지만 수행하며, 프론트와 백엔드는 JSON이라는 공용 형식으로 데이터를 주고받는다. 백엔드 언어·프레임워크로는 JavaScript(Node.js 위의 Express·NestJS)나 Python(Django·Flask·FastAPI)이 무난한 기본값으로 제시된다. 가장 중요한 보안 원칙은 "프론트는 못 믿는다" — 가격·수량·권한 같은 검증은 사용자가 조작 가능한 브라우저가 아니라 반드시 백엔드에서 다시 해야 한다는 것이다.

### 4. 프로토타입과 프로덕트 사이 — AI가 약한 곳
바이브 코딩의 흔한 실패 패턴("첫날엔 화면이 다 됐는데, 다음 주엔 로그인이 풀리고 요금이 급증한다")을 짚으며 AI가 놓치는 세 가지를 다룬다. ① **보안** — Veracode 조사에서 AI 생성 코드의 약 45%에 보안 결함이 있었고 모델이 좋아져도 비율이 줄지 않았다. "사용자 입력을 검증하고, 비밀번호는 해시로 저장하고, HTTPS를 쓰고, 흔한 취약점(주입·XSS)을 막아 달라"는 한 문장을 프롬프트에 넣는 것이 대응책이다. 에퀴팩스·소니 PSN·야후·마이스페이스·MOVEit 등 실제 유출 사고의 공통점도 "입력을 함부로 믿음/평문 비밀번호/취약점 방치"였다. ② **환경변수** — API 키를 코드에 그대로 적으면 GitHub에 올리는 순간 봇이 훔쳐가 요금 폭탄으로 이어질 수 있다(GitGuardian 집계, 2025년 유출 비밀키 약 2,865만 개, AI 서비스 키 유출은 1년 새 81% 급증). 비밀 값은 코드 밖 `.env`(그리고 `.gitignore`)로 분리해야 한다. ③ **인증 vs 인가** — 인증(로그인 확인, 실패 시 401)과 인가(권한 확인, 실패 시 403)는 다른 단계이며, 로그인 성공 시 발급되는 토큰이 이후 요청마다 신분증 역할을 한다. 비밀번호는 되돌릴 수 없는 해시(+개인마다 다른 솔트, bcrypt처럼 일부러 느린 방식)로 저장해야 하며, 쿠키(브라우저가 들고 다니는 카드)와 세션(서버 금고 속 진짜 정보)의 역할 분담도 설명한다. 마지막 O/X 점검과 "AI는 아주 빠른 신입 개발자 — 속도는 뛰어나지만 보안·비밀 관리·권한 확인은 감독이 필요하다"는 문장으로 정리한다.

### 5. 세상에 내보내기 — 배포
배포는 내 컴퓨터에만 있던 서비스를 늘 켜진 서버에 올려 누구나 주소로 접속하게 만드는 단계다. 현대 웹서비스는 보통 화면(Vercel·Netlify), 서버(Render·Railway), 데이터(Supabase 등)를 각자 잘하는 곳에 나눠 배포하며, GitHub 저장소와 연결해 두면 코드가 바뀔 때마다 자동으로 재배포된다("저장 → 올리기 → 자동 배포"). 초보가 가장 많이 막히는 세 곳은 ① 환경변수를 배포 플랫폼 설정 화면에 따로 넣지 않아서 "로컬에선 됐는데 배포하니 안 됨", ② 프론트·서버가 다른 주소에 있을 때 서버가 CORS를 허용하지 않아 브라우저가 요청을 막는 것, ③ 무료 티어가 트래픽이 늘면 유료로 전환되는 함정이다. 요금 알림 설정, 무료 한도 확인, 비밀 키 보호가 요금 폭탄을 막는 세 가지 습관으로 제시된다.

### 6. 공짜로 세상에 올리기 — 무료 서버 고르기
Heroku(2022)·Railway/Fly.io(2023~24)·Glitch(2025)가 잇달아 무료 티어를 없앤 흐름을 소개하며 "지금 무료인 것도 바뀔 수 있다"는 전제를 강조한다. 2026년 기준 쓸 만한 무료 호스팅으로 Cloudflare Pages·GitHub Pages(정적, 대역폭/구조 단순), Vercel·Netlify(프론트, 개인/상업 이용 조건 상이), Render(백엔드 API, 15분 미사용 시 잠듦), Supabase(백엔드+DB, 7일 미사용 시 일시정지), Oracle Always Free(진짜 VM, 카드 필요·설정 난이도 있음)를 표로 정리한다. 용도별 기본 선택(포트폴리오→Cloudflare/GitHub Pages, 프레임워크 프론트→Vercel, 로그인·저장 필요한 백엔드→Supabase(+Render), 직접 서버를 만져보고 싶으면 Oracle)과, 잠듦·기한 만료·요금 폭탄이라는 세 가지 무료 티어 함정을 짚는다.

### 7. 내 컴퓨터를 서버로 — 집에서 돌려보기
집 기기는 사설 IP를 쓰고 공유기(NAT)가 외부에서의 직접 접속을 막기 때문에(+유동 IP), 밖에서 내 컴퓨터에 접속하려면 전통적으로는 포트 포워딩과 DDNS가 필요했지만 보안 노출과 CGNAT(여러 집이 IP 하나를 공유)로 어려움이 많다. 요즘은 '터널' 방식(Cloudflare Tunnel, ngrok, Tailscale Funnel)이 포트를 열지 않고도 CGNAT를 통과해 바깥과 연결해 준다 — 상시용은 Cloudflare Tunnel, 잠깐 시연용은 ngrok, 개인/팀 내부 공유는 Tailscale Funnel이 적합하다. 라즈베리파이 등을 이용한 홈랩/셀프호스팅 문화도 소개하며, 결론적으로 집 서버는 원리 학습·취미에 적합하고, 남에게 안정적으로 24시간 보여줘야 하는 실제 배포는 무료 클라우드가 더 안전하고 손이 덜 간다고 정리한다.

### 8. 바이브 코딩으로 프론트-백엔드 연결하기
안정적인 순서는 "목업 화면 → 백엔드 API 붙이기 → 가짜 데이터를 실제 호출로 교체"이며, 앱 전체를 한 번에 시키기보다 "데이터 모양 → API → 화면"처럼 작게 쪼개 시키는 것이 실수를 줄인다. 연결 단계에서 가장 흔한 문제는 계약 불일치(프론트가 기대하는 데이터 모양과 백엔드가 주는 모양이 다름)이며, 근본 해결책은 엔드포인트와 요청/응답 JSON 모양을 문서(API 명세)로 먼저 적어 두고 이를 기준으로 양쪽을 짜는 것이다. 로딩/성공/에러 세 상태를 모두 준비하기, CORS·주소·환경변수를 배포 때처럼 챙기기, 기능 하나씩 화면-API-저장까지 완성하는 수직 슬라이스 방식, 단계마다 커밋해 되돌아갈 체크포인트 만들기도 실전 팁으로 제시된다. 내보내기 전 점검할 단골 실수로 프론트에만 있고 백엔드엔 없는 검증, 하드코딩된 주소·키 노출(특히 `NEXT_PUBLIC_`·`VITE_` 접두사는 브라우저에 공개된다는 뜻)을 꼽는다.

### 9. 내 서비스에 백엔드 한 겹 붙이기와 과제
과제는 두 갈래 중 하나다 — 갈래 A(주제가 없다면 Supabase 퀵스타트 같은 튜토리얼을 따라 데이터가 실제로 저장되는 앱을 만들고 기능 하나를 개선), 갈래 B(자신의 서비스에 백엔드 기능 한 겹을 붙이고 화면까지 배포). 제출 전 백엔드가 꼭 필요한 기능·필요한 엔드포인트·다뤄야 할 비밀값·호스팅 방식을 설계 한 장으로 먼저 정리하도록 안내하며, 공통 보안 체크리스트(환경변수 분리, 백엔드 검증, RLS 정책, 인가 확인, 무료 티어 한도 인지)를 제시한다. 백엔드를 둘 자리로 ① 집 컴퓨터+터널(원리 학습·시연용), ② 무료 클라우드 서버(안정적 상시 운영), ③ Supabase 같은 BaaS(가장 빠르지만 RLS를 켜지 않으면 공개 키로 누구나 데이터를 읽고 고칠 수 있어 실제로 CVE-2025-48757 같은 대량 노출 사고가 있었음)를 비교한다. 마지막으로 백엔드의 역할·네트워크 네 조각·요청의 여정과 상태 코드·AI 코드의 약점·배포와 비용을 표로 정리하며 모듈을 마무리한다.
